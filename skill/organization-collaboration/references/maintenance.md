# 岗位、角色和关系维护

维护前先判断改动属于哪一种，保留各自的唯一来源和版本。名称、描述或岗位增加不自动创建Agent、派任务、修改机器／模型配置、保存远端Role或扩大权限。

| 变化对象 | 修改与版本归属 | 不应连带改变 |
| --- | --- | --- |
| 组织协议／岗位定义 | 本skill的共同规则、岗位正文及[入口岗位导航](../SKILL.md#按本次岗位读取)；协议版本和受影响岗位定义版本 | 真实任命、专业正文、运行权限 |
| 专业角色／领域方法 | 专业角色库的稳定ID、唯一正文、来源和库版本，按该库维护约定处理 | 组织岗位、汇报对象、业务责任 |
| 实际任职／汇报关系 | 当前私密组织或项目正式记录及关系版本；有效任命方确认，注明接手点和相关任务 | 技能源代码、专业角色ID、未授权外部配置 |
| 工具或通信绑定 | 已确认的实际执行器、通道及访问证据，更新受影响任务包 | 业务归属及已成功产物；不自动切换服务或复制身份 |

## 新增或更新组织岗位

1. 核当前岗位是否足以覆盖。仅显示名称改变时保留稳定ID；不为每个专业或项目复制一套组织岗位。确有不同责任、输入、产出或汇报路径才新增ID。
2. 在本skill的`references/`维护一份岗位正文，写明稳定ID、定义版本、责任、必要上下文、交接与证据边界；在`SKILL.md`唯一岗位导航加入对应入口。新增文件不依赖仓库外路径或另一个skill的存在。
3. 比较影响：哪些派发、汇报、验收或在途任务需要变化，哪些旧上下文仍可使用；保留原有有效约束和兼容范围。合并／替换岗位先记录旧ID到新职责的映射及接手条件，不直接把旧ID改成另一种权力。
4. 发布前审查正文和最小场景、引用、完整分发及受影响端可读取性。版本与摘要随交付记录，列出改变的岗位ID、原义／新义、迁移条件及恢复方式；无需为无关岗位改写全部定义。

岗位定义版本标在各正文；共同协议版本标在入口。内容或行为变化更新受影响版本，不能同版本悄悄换义。可兼容的说明修正用patch，新增兼容岗位／能力用minor，删除、职责／必需上下文或汇报语义不兼容变化用major并说明迁移；这只是本知识协议的版本约定，不替代具体平台插件版本。专业角色库和任职关系分别维护版本，不机械同步成同一个版本号。

## 升级、停用和在途工作

普通更新先供新任务采用；在途任务记录已采用的协议、岗位及关系版本，按明确节点迁移，不因为有新版就重启、重派或丢弃旧证据。需要新岗位的端取得并读取对应版本后再接新任务；尚未更新只阻断需要该新定义的步骤，不要求全组织同时停工。

1.3.0新增`auditor`和事件追溯参考，原岗位ID、业务验收归属及已有任务引用保持兼容；已有任务包可通过引用补充所需信息，不强制转换为新schema。新任务采用新版；在途任务按交接、下一检查点或明确切换点增补执行关联及未决项，不能追溯要求旧任务重跑。历史缺失按补录标源，不伪造当时已登记。任命审计者时另核范围、独立性、监督接收者、访问与回报通道、触发方式；文件更新不等于已经任命或持续审计生效。

1.4.0在[规划与进度](planning-and-progress.md)增加局部阻塞、排障预算、E/W/Q及共享容量准入；`organization_lead`为1.3.0，`project_owner`和`executor`为1.4.0，未变的`reviewer`1.1.1及`auditor`1.0.0保留。原岗位、任务关联和权限兼容；项目在原入口确认采用版本及适用范围，仅在采用容量限制时补其配置，不默认启用示例阈值、自动调度或新服务。在途任务在明确节点引用原记录补所需信息，不重开重派，也不要求全组织同时升级。旧未验和旧版本回执保留，新版分发、读取与实际采用分别取证。

1.5.0新增按需读取的[资产归档](asset-archiving.md)，`project_owner`和`executor`为1.5.0；未变的`organization_lead`1.3.0、`reviewer`1.1.1、`auditor`1.0.0保留，不新增岗位。项目沿原正式入口确认落点政策和必要阈值，未采用继续原有效规则；在明确节点读取入口、新参考和本次岗位。新版不自动上传、迁移旧文件、改变既定验收或重派在途任务；分发、实际读取、采用与恢复／复建证据分别记录。

权限撤销、公子的新指令和当前安全修正立即约束相关在途工作，不受旧版本冻结保护。指出受影响动作，暂停或按授权停止相应执行并回报；不要声称仅更新记录就已停止远端进程。已发生的副作用和未知结果仍需原生对账。

停用、删除或替换前查明已有任职和未完成任务，指定接收责任及处理方式，按[接管规则](context-and-reporting.md#交接与接管)交还写权；未完成迁移的绑定明确待处理。不要删除唯一恢复入口、抹掉历史ID或让旧任务静默归到相近岗位。回退使用已验证版本和明确接手点；已经执行的动作不能靠回退文档撤销。

### 1.6.0：完整目标与有界 Cloud 路由

本仓独立修订：协议 1.6.0、`organization_lead` 1.4.0、`project_owner`与`executor` 1.6.0、`reviewer` 1.2.0；`auditor`版本不变。新增可选的协调层调度／Cloud 路由分工、有界主动性、各层全角色主动汇报及用户明确授权的小迭代直派边界，默认项目流程、正式任务、现任负责人和最终验收归属兼容。未采用该例外的任务继续原流程，不把小迭代授权推广给其他组织。

原“负责人交已审任务包给 Dot 代建”仍是可用分工；新版允许具备实际权限的其他调用者承担路由，明确唯一调用者和回报责任。新增规则只改变本仓规范，不代表当前协调代码支持通用目标或 Cloud 触发。新任务可引用新版；在途任务仅在明确交接点增补关系和范围，不因升级重派、补任或自动迁移写权。回退到原流程需交清原生执行、未读结果和 UNKNOWN，不能靠回退文档撤销已发生动作。历史导入摘要保留，当前本仓变更与资源摘要由固定提交追溯；分发、读取、采用及运行验证分别取证。

## 分端记录实际生效

账号权限、凭证范围、端侧连接配置和本次被委派职责分别记录。配置持久保存不代表永不失效；只在收到授权／认证异常、绑定变化或目标不明确时核必要缺项，不在每次记录前全量重验。某端已验证不推广为其他端已接入，也不要求全员持有写入凭证。

维护一份与当前任务有关的升级回执，引用各端的实际入口、协议／岗位／专业库版本或摘要、组织关系版本、加载证据和未决项；状态由负责该记录的owner核证，不能各端再建竞争的组织事实库。区分：

- 分发产物完整、目标端可取得；尚不证明原生安装。
- 安装或文件放置已完成；尚不证明本次会话读取。
- 本次已读取并能说清责任、汇报对象和准确任务关联；尚不证明持续正确执行。
- 受控场景或获授权真实任务的派发、回报、验收已观察；仅覆盖该场景和版本。

没有已验证的原生安装入口就准确记录文件读取方式，不把链接或可读目录称为安装完成。不自动安装CLI、启守护进程或创建定时监控来维持本skill。按变化范围更新必要端；已生效、未加载和不适用分别记账，旧成功回执不推广为所有端已升级。

## 切换正式记录工具

工具接入成功与项目记录迁移分别验收。切换前明确正式入口、任务保存位置、当前记录者和切换点；仅迁移需继续跟进的任务，保留旧引用到新引用的映射并核对。切换后旧队列保留历史及链接，不再独立维护当前进度。某项迁移未完成就保留它的原正式入口，不将其偷偷置于双写状态；无需先构建双向同步服务。

切换记录同时包含适用项目／任务范围、可见性与访问核对、原生执行和待补写／UNKNOWN的承接、已采用协议版本、目标端实际读取及负责人回读。所有角色从确认后的看板索引跟进，再按需展开原证据；切换未完成时不以新板空白证明没有工作。后续回退也须指定当前入口与接手点，保留新旧关联和已发生事件，不恢复成旧快照。
