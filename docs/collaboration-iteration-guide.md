## 2. 逻辑分层与多项目职责

云端Dot位于项目协调层上游，主要与用户沟通，交付完整目标、预期和边界并处理跨项目取舍。协调员在既定授权与预算内统筹各项目负责人、共享资源和 Cloud／本地路线；业务负责人决定本项目范围与最终验收，项目 Lead 准备任务、组织执行和复核，Worker 完成被委派成果。通信中转、机器在线或角色定义不会转移这些责任，具体任职仍由有效任务记录确定。

默认以完整成果交协调层，不逐实现步骤回到云端Dot转手。[独立小迭代](coordination-policy.md#3-云端dot小迭代直派)可由云端Dot直接唤起 Cloud；[协调员指挥 Cloud 路由](coordination-policy.md#4-协调员指挥-cloud-路由)是目标合同，当前 `QUERY_BLOCKER` 与信箱均不能触发该执行链。两条路线都保留唯一实际派发者与原项目验收。

每项执行明确唯一派发／续发入口及当前资产写者。两个客户端能看到同一 Agent，不表示可以同时发任务。一个项目也不必等于一个仓库、一台机器或一个常驻进程；按实际项目引用和共享资源判断边界。

### mac-work 持续在线前提与分工变更

Mac 持续在线是已接受前提，不再建设旧草案中的 VPS 常驻 Lead、Mac 离线接管或备用推理。当前主链及旧 VPS 支路分别见[架构](architecture.md)；有日期的变更依据见[历史状态](history/status-through-2026-11-03.md)。运行前提不等于全天稳定性实测。

### Task Mailbox：输入通道与验收边界

[Task Mailbox](https://github.com/CF-FE/task-mailbox-mcp)保存任务数据、事件和小结果，Mac 协调桥收件与补传；Lead 核完整输入和授权后，才决定是否显式调用执行器。信箱不会接管项目决策、自动派发或移交写权。

任务包保留原 `job_id`、`payload_hash`、tracking、结果版本与报告路由。传输去重不保证外部动作恰好一次；取消请求、原生停止、结果报告、读取 ACK 和业务验收分别取证。具体协议与客户端操作使用[服务契约](https://github.com/CF-FE/task-mailbox-mcp/blob/main/SPEC.md)和[桥的绑定与报告](https://github.com/CF-FE/task-mailbox-mcp/blob/main/mac/README.md#绑定与报告)，不在本仓复制实现或认证状态。

### Worker 与角色组合：从选择到原生执行

按[双库工作流](worker-library/README.md#从选择到真实派发)组合任务、Worker、明确后端、专业角色与显式项目合同：

1. 核任务目标、输入、验收、允许动作、资产与报告路由；角色名不产生任职。
2. 用声明能力初筛，再核目标端实际工具、模型、认证和容量；`active`不是实时可用。
3. 用离线 `prepare`固定库／模板／角色版本和资源摘要；准备稿不派发。
4. 由获准执行者绑定原生目标，取得执行、产物和回传回执；不自动替换模型、后端或在途版本。

首版[Mac 执行适配器](herdr-executor.md#职责许可与范围)只接受本 Herdr 项目的已有 Mac Agent，不是任意项目／Cloud／Win 的通用执行器。库可供选择的模板范围与实际执行器支持范围分开判断。

### 统一 Worker 的状态边界

共用契约的目标是：新 Worker 能凭明确任务包定位输入、权限与成果，而不是依赖前一个 Worker 的记忆。它不意味着整个宿主无状态。

| 对象 | 事实来源 |
| --- | --- |
| 目标、授权、范围、负责人及业务验收 | 各项目正式任务和有效决定 |
| 实际执行、未决效果与原生状态 | 原执行系统、执行 journal 及带观察时间的回执 |
| Worker 工作区与中间进度 | 所在端的活动工作区；未提交修改不能当缓存删除 |
| 模型、认证、原件与保存产物 | 对应宿主和保管者；版本化资产、唯一原件、可重建缓存分开 |
| 共享资料与交付索引 | 获准 Space／文档或原任务引用，不另养一份正式状态 |

可新建 Worker、可跨机迁移、可恢复中间进度是三项不同能力。依赖 GPU、桌面或唯一原件的任务可以继续绑定宿主；暖缓存可以复用，旧目录、参数、占用与写权不能隐式带给下一项目。

### 两类 Worker 的任务路由

| 任务条件 | 可选位置与条件 |
| --- | --- |
| 输入、依赖与检查能在获准云环境取得 | Codex Cloud；核实际环境、仓库版本、工具、网络、权限及用量 |
| 依赖 GPU、音频原件、桌面或指定宿主 | 对应机器 Worker；核本次原生目标和输入，不由连接成功推导业务授权 |
| 开发与宿主验证需要分开 | 云端开发／复核，机器验证；按 `repo + commit + path + sha256`交接，分别报告两端结果 |
| 一个池不可用或结果 UNKNOWN | 保留原执行，推进其他独立获准任务；换执行器前先对账原效果与写权 |

路由依次看授权与资产范围、所需能力、输入可达性、共享占用，最后比较等待与搬运成本。平台的文件保存能力不能代替项目交付；云任务和机器不默认共享文件、凭证或个人技能。

本项目已发布 Codex Cloud 环境，使用本仓 `main`。仓库维护规则、依赖与检查，环境管理安装、启动及访问配置。任务发起时另核实际工具、授权及原生结果入口。[当前环境记录](status.md#当前结论) · [官方环境说明](https://learn.chatgpt.com/docs/environments/cloud-environments)

## 3. 从第一条任务就保留的身份与证据

复用[任务模板](templates/pilot-task.md)及[组织任务追溯](../skill/organization-collaboration/references/task-traceability.md)，已有字段直接引用，只补影响本次决定的缺项。

| 关联 | 最小内容 |
| --- | --- |
| 项目与任务 | 原正式入口、任务／父任务、负责人、授权及验收者 |
| 输入与定义 | 需求、代码、参数、库与角色的固定版本／摘要 |
| 某次执行 | 唯一派发者、执行端、原生 task／session／pane／turn、实际目录与当前写者 |
| 信箱与事件 | 原 job／event、payload hash、tracking、结果版本；认证主体与 sender／recipient 数据分开 |
| 产物与交接 | 精确路径或工件引用、字节／摘要、实际检查、接收者和待交还范围 |
| 未决与跟进 | 原生状态、已发生效果、下一责任人、检查条件及停止预算 |

稳定 ID 用于关联，不自动提供业务幂等。正式状态、原生状态和报告同步状态分列；未知引用保持 UNKNOWN，不补造成功记录。

### 可达汇报

派发前按[可达汇报约定](../skill/organization-collaboration/references/context-and-reporting.md#派发时约定可达汇报)确定成果落点、接收者和实际可用通道。没有推送能力时，由派发者落实拉取责任与检查点，不让“已发送”代替“已读取”。

Lead 回传适配器结果使用[真实 session／turn 与原链报告](herdr-executor.md#lead-结果回传)。保存、入队、上传、精确版本读取、ACK、负责人采用与写权交还各自留证。其他执行器不能借用该 Lead 或该样本的回执。

### 各维度资源怎样组合

计算、存储、模型用量和验收能力分别计量：Cloud 配额不是 VPS 容量，GPU 空闲不代表输出目录可写，增加 Worker 不增加实际听审或负责人时间。按[容量范围与计数](../skill/organization-collaboration/references/planning-and-progress.md#容量的范围与计数)区分执行占用 E、在制承诺 W、待验成果 Q，采用本项目实际阈值，不照搬示例数字。

### ChatGPT 协作空间与本地存储怎样连通

Space 作为获准资料、交接页与精选成果入口；Git 保管固定源码；模型、原件和大产物可留原宿主。成果“外置”表示不再只存在某个 Agent 的记忆，不要求全部上传或共享挂载。

- 任务包绑定准确 Page／文件、输入版本、允许动作、输出位置、当前写者和指定接收者。页面可读不等于链接原件可读，本地路径也不等于跨端可访问。
- Dot／Cloud／Mac Lead 只沿各自实际提供且获准的工具访问；不从另一会话的连接推定自身工具或权限，不强制经 Dot 转述已有合法直达资料。
- 跨端交接分别核保存、传输受理、接收者读取及版本／摘要一致；同一资产维持唯一写者，不启用自动双向同步。
- 账号所称100G容量、具体额度与保留规则未经本仓验证；不能把它当共享卷、备份保证或必须集中上传的理由。

只验证本次任务依赖的访问边。一项资料入口未就绪不阻塞其他已获准输入；新增对象存储／NAS等能力需要已有交接方式确实无法满足需求的证据。

## 4. 分阶段迭代

当前按[弱连接下的进度与迭代](coordination-policy.md#弱连接下的进度与迭代)推进，先用真实任务验证本地交办和验收，再依据实际等待决定后续优化。

阶段描述依赖，不是逐任务增加审批。独立工作可并行；本表不授予执行、部署、自动化或新模型调用权限。

| 阶段 | 要回答的问题 | 最小证据与边界 |
| --- | --- | --- |
| I0 绑定目标与范围 | 谁做哪项成果，何时可开始／停止 | 一项任务的输入、权限、写者、预算和验收完整；不以全组织盘点为前置 |
| I1 单条闭环 | 选定入口能否准确执行并交付 | 原生引用、固定产物、指定接收者回读及限定验收；现有 Mac 显式切片可复用，其他入口不继承 |
| I2 长执行与短控制分离 | 长任务期间能否继续查询和协调 | 原任务仍被正确观察，另一项独立获准请求取得结果；不虚称自动回调或唤醒 |
| I3 多项目同时推进 | 独立项目能否重叠，局部阻塞能否隔离 | 至少两个项目有活动重叠和有效成果；采用云机混合时另核两端交接，分别验收 |
| I4 降低路由与上下文开销 | 是否反复定位归属、搬运大日志或漏跟进 | 相同输入／质量口径比较精确引用、摘要与按需读取；出现错关联或漏控制指令即撤回 |
| I5 原执行对账 | 超时后能否找回效果、产物与未交报告 | 沿原引用恢复观察，保留 UNKNOWN和写权；不以新任务替代旧执行 |
| I6 有界主动性 | 哪些事件值得自动观察或处置 | 先观察，再凭明确规则、权限、预算、停止点验证获准动作；不默认无人值守业务执行 |

I3 才能支持“多项目同时推进”的结论；一个合成回合不能替代它。必要的关联与对账从 I1 就应具备，后续阶段不要求先部署通用调度平台。

## 5. 多项目验收情境

这些是后续可选验证情境，不是已经执行的测试或故障注入授权。

| 情境 | 必须看见的区别 |
| --- | --- |
| A 长任务期间 B 继续 | 时间与原生引用证明活动重叠；两个 chat 或串行完成不足以证明 |
| A 局部受阻，B 独立推进 | A的未知占用保留；B输入、权限和资源独立成立 |
| 云端开发交机器验证 | 固定版本确实到达；云端测试与目标宿主检查分别报告 |
| 两项目争用GPU、目录或验收者 | 真实共享范围有准入与释放依据；不同目录名不自动证明无冲突 |
| 新Worker接续或原结果回报中断 | 先核原执行、保存产物和写权，再沿准确关联接续或补交；不重做成功单元 |
| 两项目分别交付 | 产物、复核与负责人决定分别归各项目；汇总通知不代替验收 |

实际准备和停止规则见[试点指引](pilot.md)，组织能力与资料评阅见[评测资料](organization-collaboration/README.md)。

## 6. 优化机制的采用与取舍

### 事件与上下文

区分控制指令、原任务结果、新业务候选和普通日志。已有准确绑定的结果沿原任务交付；摘要可合并日志，但须保留版本、失败、UNKNOWN、撤权、已发生效果和未交还写权。长原文只按需取回，不将各项目私密全文汇成一个共享记忆。

### 何时增加组件

| 候选 | 需要的实际触发 | 撤回条件 |
| --- | --- | --- |
| Router／分域协调 | 精确引用仍不能解决持续响应或权限域瓶颈 | 调用与维护成本增加，或出现第二派发／决策入口 |
| 信箱／Outbox扩展 | 现有真实回执缺少必要交接事实 | 重复状态库、错误去重或自动执行超出授权 |
| 确定性健康恢复 | 明确无人值守需求，能区分意外退出与有意停止 | 无穷重启掩盖配置／认证故障，或不能尊重停止 |
| LLM Watchdog | 结构化状态解释不了的反复停滞，诊断确能减少人工成本 | 误判、额外费用或擅自改提示词／重派／接管写权 |
| 独立执行环境 | 实际依赖冲突、安全边界或并发收益需要 | 隔离与维护成本超过已测收益 |

### 资源配置是可调参数

先按真实负载比较并发调整、日志／缓存治理与扩容；Mac会话、VPS服务、Cloud配额及执行机分别计量。旧VPS起始规格不是架构上限，能扩容也不是新增组件的理由。硬件调整不自动改变资产归属或赋予新执行权限。

## 7. 持久状态、恢复与退出

保留任务／输入映射、原生引用、未决效果、写者、待交付报告和下一责任人。执行已结束且资源确实释放时可解除计算占用；产物交付、验收和写权交还仍分别核对。具体 UNKNOWN、恢复与退出动作沿[试点规则](pilot.md#等待未知与恢复)，适配器 journal 沿其[状态合同](herdr-executor.md#状态产物与保全)。

撤回优化先停止新准入，交清已发执行和未决项，再沿原入口收尾；不删除关联或自动换执行器重做。旧 Lody 逐任务交接见[接收边界](organization-collaboration/README.md#退出与运行交接待办的责任)。

## 8. 每轮怎样作决定

每轮只解决一个具体问题，比较保留现状、改现有流程与增加最小组件。按相同输入和质量口径记录：多项目有效重叠、人工转述与定位次数、等待年龄、重复／错关联、UNKNOWN对账、每项已验收成果成本及真实资源峰值。样本不足不编造p95、提效比例或通用最低配置。

在原任务写清“问题与证据 → 最小变化及预算 → 验证与产物 → 保留／调整／撤回依据 → 下一责任人”即可，不新建一套Project schema或全局编号服务。

## 9. 参考与不照搬的边界
