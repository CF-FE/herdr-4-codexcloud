# 云端Dot 与常驻项目协调员：联络与跟进方案

v0.4 · 2026-11-04；创建职责说明更新于 2026-11-09 · **本页是协调员、项目负责人和 Worker 生命周期的设计依据**。云端Dot上游定位、协调员调度权限、有界主动性、主动汇报、小迭代直派及 Cloud 路由职责统一见[协作约定](coordination-policy.md)。第 3 节定联络归属，第 4 节定初始化、交接、恢复和 [hooks](#lifecycle-hooks)，第 6 节给出验收条件。本机协调核心与隔离联调已实现。凡人首件由公子转交原端凭据，第二件通过已登录的原云端Dot对话直接提交、读回并确认。哪些能实际运行，以[本机交付与运行](#7-本机交付与运行)及[当前状态](status.md)为准。

## 1. 建议与取舍

在已约定持续在线的 Mac 上设置一个可恢复的**协调入口**。当前只读联络中，云端Dot向它提交请求，获得固定编号；协调入口负责找对人、拿回答复、追到下一责任人，并把结果交回原云端Dot。项目负责人保留业务决定和验收权。普通状态跟进由确定性程序承担，需要判断时才联系获授权的负责人或执行者。目标架构中的协调员还在授权内统筹项目负责人、跨项目资源与 Cloud／本地路线；这份较广的组织调度职责不代表下述程序已经具备通用任务派发或 Cloud 创建能力。

| 要保留的目标 | 实际矛盾 | 采用的做法 |
| --- | --- | --- |
| 云端Dot可以一直找到协调员 | 常驻模型在线也会丢失会话、任职关系和上次等待条件 | 常驻的是逻辑地址、请求台账与恢复触发器。模型按需参与，重启后按原请求继续 |
| 主动找到实际负责人 | 进程、岗位模板、Issue 写者、历史任命分别证明不同事实。凡人已经有专职负责人受理记录 | 优先恢复已有任职的联系地址。核查任职、验证本次答复来源、确认接手分别留证 |
| 主动解决阻塞 | 查询生成进度、安排听检、重新合成音频需要不同权限。一个通用“处理任务”操作很容易越界 | 首版只开放 `QUERY_BLOCKER`。需要措施时记录责任、条件和现有授权，负责人据此处理。执行或新增授权有独立动作和凭据 |
| 跨项目可靠联系 | 相同账号的 Mailbox 客户端能填写相同 sender 或 recipient。角色名和摘要不能识别云端Dot或负责人 | 请求和答复都绑定可验证的原生主体。按主体、项目、动作分别授权读取、提交、报告和确认 |
| 负责人缺失时补位 | 联系失败时旧负责人可能仍在生产，并持有写权 | 失联进入恢复分支。只有任命权威确认空缺、原写权已处理且有明确授权，才进入创建分支 |

若已有受控直连端点，首轮就复用它。直连解决一次投递，协调入口承担云端Dot离线、请求超时或负责人换任后的持续跟进。若现场已有入口同时满足寻址、持久跟进和原请求读回，可沿它扩展同一合同，省去另起服务。

## 3. 谁维护什么

需要评审的架构变更（`ARCHITECTURE_GATE`）是新增跨项目请求的跟进责任，以及桥向已认证的本机协调入口交付完整请求／接收结果的合同。现有执行适配器的通过范围是单项目显式调用，新的权限及交付合同处于提议状态。

| 所在位置 | 唯一负责的事实与动作 |
| --- | --- |
| 云端Dot及有效任命方 | 云端Dot在协调层上游向用户负责，交清完整目标、预期和边界，接收结果、协调跨项目取舍，处理确需公子决定的事项。每个请求固定一个可验证的云端Dot调用端及读回方式；任命仍由有效任命方决定 |
| Mac 协调入口，本协作仓维护 | 当前维护项目路由、经核验的任职引用与代次、请求和动作台账、等待条件、通知去重，联系负责人并收回证据。目标职责扩展为授权内统筹各项目负责人、共享资源及执行路线，见[Cloud 路由合同](coordination-policy.md#4-协调员指挥-cloud-路由)，不是当前实现声明 |
| Task Mailbox／Mac 桥，服务仓维护 | 维护传输、认证、原 job／event／结果版本和 collector。需要的本机交付与结果入队扩展由该仓定义，按版本化接口与协调入口交换数据 |
| 凡人或其他项目 | 原正式记录拥有任命依据、业务进度和验收决定。负责人组织执行、核对原件、指定下一步。执行者对其实际执行与产物负责 |
| 原生联系／执行端 | 验证实际接收目标、允许动作、代次和效果。项目已有的联系通道优先。需要 Herdr 时固定真实 session／pane／Agent、目录、有效环境和调用预算 |

首版只需一个本地状态库、一位运行写者和一个状态 CLI。项目目录保存 `project_id`、仓库／原看板引用、任职来源与版本、负责人主体、受控联系地址、允许的运行环境与动作、报告路由、原在途引用及交接点。私密地址和凭据引用留在受限配置。业务进度从原项目读取，协调台账只保存与本次请求相关的事实及来源。

**任务按成果归属路由，由谁操作工具另记。** 规则沿用[组织委派约定](../skill/organization-collaboration/references/organization-lead.md#接手和分配)：

| 收到的任务 | 谁接、谁验 |
| --- | --- |
| 改变某项目资产、交付或消耗其生产许可 | 默认云端Dot → 协调员 → 该项目现任负责人。负责人组织实施，协调员按授权安排执行路线；当前可沿获准通道请云端Dot依已审任务包代建。符合[小迭代直派条件](coordination-policy.md#3-云端dot小迭代直派)时可简化派发，负责人仍在任命范围内决定项目事项、集成和验收。解除生产冻结或增加预算须由相应授权方决定。负责人缺位时保留原请求 |
| 确无项目归属，如跨项目容量汇总 | 云端Dot可把组织任务明确委托给协调员，写明原任务、可读范围、期限、预算和验收人；协调员可在授权内自办或委派 Worker，向云端Dot交付。汇总产生的项目实施项分别关联并转给对应负责人 |
| 归属不清或涉及多个项目的写入 | 协调员负责澄清、跟进；可继续有独立授权的只读核查。确定各项目及资产边界后分派，保留父请求。不能把未分类任务登记为“非项目”绕开负责人 |

既有只读业务沿用 `QUERY_BLOCKER`。需交给现任负责人承接完整目标时，使用[受控完整目标交办](goal-handoff.md)，独立绑定现任负责人、原任务、范围、一次派发预算及接手/进展回报。它不开放虚拟项目、自动负责人创建或 Cloud 创建；部署与具体业务准入另核。信箱提交不能在查询正文夹带目标交办并声称执行已受理。独立连通性探针保持原范围。完整目标缺实际原生入口时，沿原 job 回报待承接与下一责任人。协调员的[有界主动性](coordination-policy.md#协调员的有界主动性)覆盖授权内风险发现、未完成事项推进、资源协调和改进提议；`tick` 检查到期项不等于这些通用行动已自动化。

### 可信入口与传输

拟采用的首轮路径如下，去程与回程共用云端Dot保存的原 job。

```text
去程   云端Dot → Task Mailbox → Mac 桥 → 协调入口 → 已验证的原生联系通道 → 项目负责人
回程   负责人答复 → 协调入口核任职、版本和证据 → 原桥补传 → 原 job 的结果版本 → 云端Dot实际读回
```

1. 云端Dot原生端提供实际主体或可验证的授权证明。协调入口核对其绑定、项目、动作、期限和预算，然后接单。答复也要通过已绑定负责人端核验。任意客户端可填写的名称、`whoami` 的共享账号和同一明文信箱里可读的 nonce，单独均不足以证明角色。
2. 能复用既有受信原生通道时，沿该通道验证双方。若只剩共享账号，先做不含私密业务内容的连通预检，状态记为身份待绑定。正式多主体访问须由实际服务入口实现受信主体与项目权限，覆盖已知 job ID 的直接读取、报告、取消和 ACK。消息签名只解决来源，跨项目保密还需要读取控制。新增凭据或持久权限单独核准。
3. 原桥的唯一 collector 通过私有 Unix socket 交付获准的原件，将协调员结果按原事件写入原桥待发队列，再由原 collector 上传。协调员按原请求去重，双方核对完整请求和最终结果的摘要。接口的安装、授权和回执见[本机桥端口](#local-bridge-port)。
4. 对云端Dot暴露四个逻辑操作，即提交请求、查询进展、读取指定结果和查询健康。优先沿现有获准传输表达，状态／健康查询返回带观察时间的快照。云端Dot保存原 `job_id`，按它读回明确的版本和摘要。现有事件筛选沿原任务的收件人，监听云端Dot别名不足以找到它发给协调员的请求结果。云端Dot可用时主动拉取，自动唤醒能力另行取证。[事件筛选与结果读取](https://github.com/CF-FE/task-mailbox-mcp/blob/6179582aa7253016a96e3036ba031fd614e29ecb/mailbox_store.py#L256-L341)

### 请求、答复和等待

幂等记录以“经验证的发送方、项目、动作类型、幂等键”联合定位。在授权检查后比较规范化输入摘要，包括目标代次和期限。同键同内容找回原请求，同键异内容拒绝并保留原件，避免他项目探测到既有记录。

| 对象 | 最小记录 |
| --- | --- |
| 联系请求 | schema 版本、项目、`request_id`、原 `task_ref`、关联 ID、幂等键、`QUERY_BLOCKER`、目标任职版本、经验证的发送方、授权引用、期限、预算与证据引用 |
| 联系动作 | `action_id`、原生目标、预期代次、输入摘要、发前意图、实际提交／收件／回复凭据与发生时间。每次外部动作有一个执行者 |
| 负责人答复 | 原项目／请求／动作、答复主体及代次、观察时间、阻塞与影响、证据位置、已核与未核项、下一责任人和触发条件。识别到迟到的旧代答复时，附回原请求供对账 |
| 云端Dot交付 | 原 job、结果版本与摘要、指定云端Dot实际读取凭据、云端Dot提取的阻塞和下一步。需要通知时按请求、实质状态变化和接收者去重 |
| 任何等待 | 跟进责任仍属协调入口，另记当前动作责任人、等待原因、最后证据、下次检查时间或事件、截止预算和升级对象。超过约定时间带着原关联升级，继续保留未决项 |

传输分别记录持久化、提交到通道、目标确认收件和精确结果读取。协调分别记录核验任职、等待答复、需要决策、答复已交付。执行保留原生状态、已发生效果及 `UNKNOWN`。验收分别记录技术验证、独立质量复核和负责人决定。协调员可把“阻塞查询已答复”交给云端Dot，同时让原生产任务继续等待听检。

查询、补传使用原 ID，并受持久化的次数与时间预算约束。状态 CLI 显示最近成功收件、最近失败、队列与最老等待项、负责人最后响应和下一检查点。无法查询宿主时保留最后观察时间，云端Dot可以识别过期快照。协调入口自身的恢复见下节。

失败按证据分类。权威登记确认空缺记“无负责人”，查不到受控登记记“任职未知”。身份不符拒收并留证。认证／路由故障记“通道不可用”，只有原生端明确报告离线才记“离线”。已知请求未受理可在原预算内恢复。可能已投递而失去回执记 `UNKNOWN`，沿原动作对账。只有绑定负责人明确确认收件，才能记“已收未答”。取消请求立即阻止新动作，实际停止、既有结果和写权分别核对。

## 4. 三类 Agent 的生命周期

下表是管理职责。其状态由任命、接手和交还记录驱动。Herdr 只描述它能看到的运行实例；换 pane、重连或换模型都不会自动改变职责。

| 对象 | 稳定身份与唯一性 | 谁让它生效 | 何时退出 |
| --- | --- | --- | --- |
| 常驻协调员 | 同一组织范围一个固定逻辑入口，对应一份权威台账；模型可按需运行 | 有效任命方确定职责与权限；业务协调员之外的受信宿主管理入口初始化／恢复 Mac Herdr 绑定，云端Dot从自己的端点验证往返 | 停收新单，移交待办、未读结果与下一检查点，再撤掉旧写入口 |
| 项目负责人 | 每个项目在一个任职代次只有一位有效负责人；可以暂时空缺 | 有效任命方指定；协调员据此安排创建、绑定或交接，核验身份与联系，候任人明确接手后激活 | 任期结束、撤权或换任时停止旧代新增派发，原任务与迟到证据仍可追溯 |
| Worker | 模板定义可复用；实际执行绑定原任务、执行尝试、目标和资产范围 | 项目负责人或获准唯一派发者按任务单元选择、复用或创建，核权后沿原生入口派发；Worker 只对本次执行和报告负责 | 核验原件、处理未决效果、显式交还绑定；只有本次专建资源才按原 ID 清理 |

三类对象的职责决定、技术创建与实际接手分别留证。组织角色和本地 Worker 的运行载体是 Herdr；唯一宿主例外是获准 Codex 路由提交的具体 Cloud 作业，组织绑定与验收归属保留。谁实际操作、何时需宿主管理者及所需原生引用，统一见[创建职责速查](agent-hosts.md#role-creation-responsibility)。App 聊天和临时子代理不因收到任务而成为组织岗位；Decision Service 仅在合法候选中推荐动作或模型配置，不任命、创建、恢复或激活角色。

| `working`／`blocked` | 前者表示观察到活动，后者原因依集成而异，可能是问答、审批或错误；未识别的提示也可能显示 idle | 核实际请求、产物或对话框；需要决定时找有权限的一方。禁止自动批准或以活动时长报告业务进度 |
| `idle`／`done` | 二者均可输入；CLI 的 `done` 表示回到 idle、完成提示尚未标为已看。客户端各自的提示可不同。`agent prompt --wait` 不识别本次 turn，旧回合也可能满足等待 | 只触发一次原任务结果核查。以执行关联、输入版本和实际产物回报；不从徽标生成完成、交还或验收 |
| `unknown`、查不到 Agent、单次等待超时 | 依次可能是已识别 Agent 但状态难分类、当前视图未发现、未及时观察到条件；不等于同一事实 | 原样带来源和时间保存。业务效果不能判断时另记 `UNKNOWN`，沿原动作对账，不能仅凭这些观察重发 |
| detach、server 重启、升级交接 | 客户端 detach 时原进程可继续；冷启动恢复的是布局，有有效集成与会话引用时才可能恢复对话；[live handoff](https://github.com/herdrdev/herdr/blob/2ecf19a92fc3a7fff75b6ce3655ef04f4625ec01/docs/next/website/src/content/docs/session-state.mdx#L117-L127) 也可能中断在途请求和等待 | 按原目标核进程、原件、锁、回执。重现屏幕或恢复对话都不能证明原任务续跑；主机重启另验 |

### 协调员：谁初始化，找不到时怎么办

1. **首次开通。** 有效任命方确定职责与权限，云端Dot指定或转达有效授权。项目协调层的宿主管理入口在业务协调员之外。已指定的宿主管理者核既有任职和在途工作，通过[组织角色受控创建](agent-hosts.md#controlled-role-creation)准备 Mac Herdr 候选，再登记稳定 ID、受信端点、权威台账身份和当前写者。已有登记时沿原绑定对账。云端Dot从自己的入口核对真实身份和接手答复后才开始使用。
2. **日常值守。** 宿主可在无模型进程时保留任职、待办、检查条件、游标和未读结果；重启沿原库恢复。云端Dot在取得可验证的受理回执前负责跟进，受理后由协调员负责，即使云端Dot离线也保留结果待取。分别展示宿主管理面、台账、业务端点及最近一次云端Dot往返的健康与观察时间。
3. **云端Dot找不到协调员。** 保存原请求、目标与截止时间，先查原受理／结果，再经独立的受信管理入口查登记。仅当权威登记证实从未初始化且有开通授权时才首次建；登记有效但进程退出则恢复**原**实例职责与原库。主动暂停／退役遵从原决定；权限不足交授权方，宿主或登记不可达则由云端Dot按有界间隔跟进，超预算向宿主维护者升级一次。原库丢失或绑定矛盾时停止写入，不能另建空库、自任协调员、切 VPS 或绕过负责人。宿主管理入口也失联时，恢复责任终止递归于已指定的宿主维护者，不再创建监督 Agent。
4. **交替与退役。** 先在实际入口停止接新单和新增派发，保留原请求回传、读取与对账；接手方逐项确认未决效果、写者、未读结果与下次检查点。切换唯一登记及写者代次，旧端回归只能补交原证据。旧备份须与库外已知的最高代次、原生效果核齐后才恢复写入。永久撤销写权后，原地址保留只读去向与历史引用。

Watchdog 负责发现异常，例如“负责人到期未回”。本机 `tick` 能登记到期提醒。协调员还要查明是等审批、未送达，还是结果未回传，联系有权处理的人，并把原答复交还云端Dot。协调员自身的进程恢复由宿主管理者负责；超时不能触发重做业务任务。

### 项目负责人：恢复联系、补位与交接

1. **发现。** 协调员查原项目的任命记录、既有负责人、未决创建、在途任务和写者。失联先恢复原通道。无可证现任记“任职待核”，只有任命权威确认才记空缺。有负责人但暂不在线，不使项目自动进入招聘或换任。
2. **补位。** 协调员依据有效任命安排恢复、绑定现有候选或通过[Mac Codex 受控入口新建](agent-hosts.md#controlled-role-creation)，与当前 `codex-cli:mac` 联系和目标运行合同一致。首次 session 初始化、受限定位配置等宿主管理动作由有权维护者执行。新建沿原台账核空缺、预期代次及写权交接，登记原创建 ID 和启动意图。回执丢失时沿同一绑定对账。原生创建取得候选，任命与激活沿原权威记录办理。
3. **接手与在任。** 验证候选主体、项目边界、能力与真实双向联系，交接目标、资产、在途执行／审批／未知效果、报告地址、下一检查点，以及旧写者的释放或范围拆分凭据。候任明确接手，才按预期代次激活。在最终可控派发／写入点核当前代次、动作 ID 和权限。不能隔离可绕过入口的旧写者时，冲突范围维持只读。
4. **代办与更替。** 借 Worker 听检或请云端Dot代建任务均不换任；真正的临时代任也须有任命范围、期限、交接和新代次。到期／撤权即挡住相关新动作。已经受理的执行留在原目标对账；旧代回执按原任务存证，由当前有效负责人决定采用。无人接手时协调员继续跟进，独立获准的检查可做，相关新决策与写入等待。

### Worker：从选用到交还

1. **选用。** 负责人或获准唯一派发者按本次任务单元，用[双库](worker-library/README.md#离线查询与准备)选 Worker 模板、后端和专业角色。复用实例先核目标、空闲原因、遗留任务及上下文隔离。确需新建且有权限时，使用[受控入口](agent-hosts.md#controlled-role-creation)绑定原任务、派发授权及输入摘要。获准的具体 Cloud 作业仍由本单唯一 Codex 路由提交并收回 task ID。跨项目借算力或专长沿本次材料和动作权限办理，成果由原验收者核收。
2. **派发。** 任务包固定原任务、输入与验收、委派人、报告对象、有效代次、实例及执行尝试、预算和唯一写者。先持久登记意图，再按真实地址提交。只有具备幂等合同的传输才按原 ID 重交；Herdr prompt 可能已送达就只查原动作，同一 ID 不能防止再次执行。确需新执行，先处置原效果／写权，经有效委派后另立尝试并关联前次。首版适配器只显式使用已有 Mac Agent，不负责启动 Worker。
3. **运行与中断。** Worker 交回带关联的进展、阻塞、审批或产物。失联先核原机、进程／子任务、锁、产物及报告；暂停、撤权、取消请求不证明实际停止。冲突资源在效果未知时保留；若原生证据已证实算力释放，只有报告回填未知，可释放算力并保留回传责任。调度者失联期间不扩大原授权，不领取下一项。
4. **交付与退出。** 核原任务、产物版本／摘要及原件；按项目标准安排独立复核和负责人决定。适配器 `COLLECTED` 表示核到报告及所列文件，`RELEASED` 需要 Lead 显式记录交还；两者都不等于业务验收。借用实例解除本次绑定、清理本次权限与上下文后才可复用；专建实例核无未决效果及其他写者再按创建 ID 清理。保留原报告、接收者和恢复引用。

**三个岗位分别如何使用：**

- **协调员**沿本机持久事件找待办：`REQUEST_ACCEPTED` 后跟进，`VERIFIED_REPLY` 后准备结果，`CLOUD_DOT_READ` 单记已读。它们是[协调台账事件](../scripts/project_coordinator.py)，不是 Herdr hook。目前 launchd 配置只运行本地 `tick` 检查到期项，没有来自云端Dot的通用唤醒 hook。若协调员采用按需模型，恢复仍读原台账。
- **项目负责人**可用自己实际运行端的会话／审批提示找回原请求。即使担任 Lead 的恰是 Codex，也只有绑定自己真实 session／turn 的结构化报告才能走桥。接手需任命、交接及可核答复；暂停或换任需任命方记录。不能用 Worker 的 Stop 代签负责人。
- **Worker**用其后端原生信号报告“该检查哪里”。Shell Worker 沿命令退出和产物，Cloud Worker 沿其获准的原生执行引用与结果，均不伪造 Herdr 或 Codex 事件。核验原件、独立听检、释放资源与验收分别留据；目标端无 hook 时由当前责任人按原请求限次查询。

**处理规则。** hook 是观察或补传的触发器。仅接收允许来源和最少字段，不把终端输出／任务正文当作指令、认证或授权。按原生事件键及本地关联去重，同键异内容留作冲突；没有稳定事件键时只用作刷新提示。重复、乱序、迟到及缺失都回到原请求与当前代次核查。旧代证据可追加，不能据此恢复旧写权。只有实质变化或需决策时通知云端Dot。不为了统一接口给各端安装新 hook，也不以一次回调独立触发新建 Agent、重派、审批或结案。

**交付边界。** 三类角色的技术新建与原意图对账共用[受控入口](agent-hosts.md#controlled-role-creation)。独立宿主管理登记自动化、协调员写者切换与退役、角色任命激活、任意任务自动派发及 Herdr 事件订阅仍各沿本节的责任和证据办理。已有[现任负责人联络与恢复](#nonblocking-contact)和[单件完整目标交办](goal-handoff.md)。Mac 原工作流新单元的合成工程证据见[模型配置应用](agent-hosts.md#decision-model-selection)，旧显式适配器的单次真实 Mac Worker 范围见[执行适配器](herdr-executor.md#验收记录)。新入口的宿主采用见[当前状态](status.md#当前结论)。

## 5. 凡人首轮如何验

**请求内容**　“请先核对现场所称的 22 段与 Issue 中的‘1 段已读回、21 段已提交’，分别属于哪个批次、输入版本和观察时点。能对应的按已生成、待技术读回、待听检分组，暂时无法对应的保留各自计数。请据此指出当前阻塞、下一责任人、检查条件及证据引用。”范围是查询、联系和读回，额外音频生成次数及生产资产写入次数均为 **0**。

1. 云端Dot从自己的获准入口提交，保存原请求与 job。协调入口登记跟进责任，沿项目导航找到 Project #5、生产 Issue #2 和受控任职索引。优先核历史负责人，不能从看板条目或正在工作的进程推定新任职。[项目入口](https://github.com/CF-FE/fanren-work/issues/9)
2. 在获准联系通道定向发送查询，核负责人本次收件或直接取得其关联答复。若生产 pane 正忙，走既有独立联系通道或排队等待。采用只读工具与最小环境变量白名单，隔离生产命令、写凭据和输出目录。模型提示词中的约束不能替代执行端的权限控制。
3. 负责人沿原执行引用、批次、产物清单、进程／锁、待批事项及回传状态定位阻塞。每项结论注明来源和时间。可只交受控清单引用及分组计数，私人音频留在原宿主。暂时只能核一段时，明确余下的观察缺口。[生产记录](https://github.com/CF-FE/fanren-work/issues/2)
4. 云端Dot读全原请求对应的精确结果，核版本和摘要，并能向公子报告“阻塞是什么、谁接手、下一次看什么”。至此验收**联络闭环**。若阻塞是听检尚无人承接，协调入口继续跟踪项目负责人安排独立听检，取得接手和后续处理证据。由当前生效代次的负责人核实约定的解除条件后，另记**解阻闭环**。例如安排短缺可用合格审查者实际接手为证，音质待验则需实际听检结果。正式整集验收继续遵循凡人项目标准。

若 P0 无法取得历史负责人的现行受控地址，交付项是一个可继续跟进的阻塞记录，包含缺失证据、保管方、已查范围、下一检查点和云端Dot的读取凭据。联络成功、负责人空缺和重新生产三项均不能据此成立。

例如，若云端Dot找不到协调员，而 win-work 上制作 Worker 仍在跑：云端Dot保留原查询，先走宿主恢复入口；协调员恢复后查最后的 Lody 任命、云端Dot直派的原执行与现有产物，三者分开记。制作端可以补交原回执；它不能自动接任。任职待核期间只推进独立获准的只读对账。核实接手后，由现任负责人安排独立听检、给出下一步；云端Dot沿原请求读回。全程新增音频为零。

### 原桥交付与结果回传

两端分别安装。Mac 桥管理自己的 collector、端口策略、原件与发件队列。协调员在自己的台账保存受理、结果版本和入队回执。双方通过本机 socket 交换数据，运行时不跨仓导入模块。运营人员可使用固定发布中的 [coordinator_bridge.py](../scripts/coordinator_bridge.py) 核验以下步骤。

| 操作 | 核验依据 |
| --- | --- |
| `probe` | 两端核本机端口及挑战应答，返回 `PORT_VERIFIED`。专用探测密钥只允许取协议能力 |
| `deliver --job-id …` | 原桥已从信箱核到完整 payload。本机策略须另有原生发送方、原 job 和摘要、正式 Project 条目及其来源证据。协调员复核项目登记、目标、代次、只读预算与幂等键后受理 |
| `enqueue --project-id … --request-id … --version N` | 以台账中已持久化的版本生成结果，先按原 job/event 查原桥。相同事件沿用原回执，冲突拒绝。入队 `PENDING` 后由原 collector 补传，`SENT` 含信箱实际版本 |
| `pump` | 每轮只跟进私有配置中固定的一条查询，至多交付一个连续结果版本。受理与结果入队可跨进程恢复。未设置试点时返回 `NO_PILOT` |

Mac 桥侧的 `coordinator-port.json` 与桥配置同目录。协调员侧的 `bridge-port.json` 与其 `state/` 同目录。两份私有配置由宿主管理者维护，文件权限 0600，直接父目录 0700。探测配置使用独立的 `probe-` 密钥、空业务授权和 `pilot:null`。正式试点另行固定发送主体、项目、请求号、原 job、摘要及回程，业务授权只覆盖该件。任职、来源与读回证据应来自各自受控端。共享信箱账号下的 sender 字段、桌面代签或探测成功均不足以填充这些证据。

首轮接入沿用原桥的网络轮询和 OAuth，协调员只调用本地端口。原桥待发队列保存结果后，网络错误沿原 event 对账和补传。云端Dot 是否实际读回，仍须由其原生端提供同一 job、信箱版本、结果摘要和答复内容。Mac 上读取待发记录只证明本机已入队。

启用时先在正式安装根准备两份私有配置。按服务仓的[密钥准备与轮换说明](https://github.com/CF-FE/task-mailbox-mcp/blob/b6dc6b6dafff08f4ba25ddd999df4e679bb4a802/mac/README.md#协调员本地签名探针)将已批准的探测密钥绑定到 `probe-` 身份，由原 collector 加载策略。用已安装解释器运行下列命令。只有 `PORT_VERIFIED` 证明实际安装的双方完成了签名握手。需要持续运行时，在当前用户 LaunchAgents 安装并加载本版的 `bridge-pump.plist`，服务名为 `io.projectcoordinator.bridge-pump`。两端在业务凭据核实后分别绑定同一原件，完整流程才进入受理。

```bash
"$PYTHON" -I -B "$RELEASE/scripts/coordinator_bridge.py" --config "$APP/bridge-port.json" probe
"$PYTHON" -I -B "$RELEASE/scripts/coordinator_bridge.py" --config "$APP/bridge-port.json" pump
```

首次受理持久保存原生通道、主体以及任务与发送证据引用。出件时复核同一绑定。升级前已受理且缺这些证据的记录保留原台账，只读对账，由原端补证。回退时先停桥端口的 pump，再依两仓各自的手册恢复固定发布，保留已提交事件与原队列。

### 日常 Herdr 原任务待办

**审批子工作流已实现并在 Mac 采用。** 当前绑定协调员沿原生会话发 `COORD_APPROVAL_PREPARE` 提案，由原 watcher 登记，不要求协调员直接写台账；hook 在用户活动时提示，受信主会话记录者的答复由原 watcher 回流到原检查点。提问受理或不断 `RECHECK` 仍不等于用户收到；通知不即时，真实 UI、自然审批及业务验收待自然单。具体提案、回流和升级合同只维护于[审批子工作流设计](approval-workflow.md)。

协调员派出需要收回结果的工作前，登记原任务、回执或派发依据、现任负责人代次、下一动作、责任岗位和最迟复查时间。收到部分回执、需要负责人决定或暂时联系不上时，已有项继续跟进，漏登的沿原单补录。先留待办，再写 GitHub 摘要。协调员换事、恢复绑定或接到内部提醒时，读取该项目未结项，按原生记录判断原件是否已经送达。

**协调员在本人的原生会话使用一条独立消息登记。** 整条消息只有一行：`COORD_FOLLOWUP ` 后接 JSON，无引号包裹、代码围栏或说明段。仅在确实作出这个决定时发出该格式。用户输入、转发材料、工具输出和其他会话不能登记。正文与证据引用是待审数据，登记只产生内部跟进责任。首次登记或更新后可用 `herdr_role_contact.py show PROJECT` 回读 `role_followups`，私有原始材料保留在原端。

| op | 必填字段与时机 |
|---|---|
| `put` | `project_id, followup_key, generation, task_ref, receipt_ref, next_action, action_owner, next_check_at`。同一原任务里的同一动作使用稳定键，时间须带时区。每个不同的决定可单列下一项。 |
| `record` | `project_id, followup_key, generation, expected_revision, outcome, evidence_ref`。读原项取当前修订号。已有对应决定或办结回执用 `CLOSED`；接到提醒后仍需等条件，用 `RECHECK` 并给新的处置依据和未来 `next_check_at`；尚未发提醒可用 `DEFER` 调整检查点。投递结果未知先在原线程对账。 |

**有实际输入条件的待办可采用证据或截止触发。** `put` 可附 `trigger`，包含 `task_id`、任务内 JSON 相对 `path`、顶层实质字段名列表 `fields`、这些字段规范化 JSON 的 `baseline_sha256`（尚无原件可为 `null`），以及可选的 `deadline_at`。来源限本机 `ProjectWorkflowTools/state/<project_id>/<task_id>/` 内的有界普通 JSON 文件。只选实际接收者有权维护的原件或最小可信投影，字段应关联原生回执、决定或材料版本；观察时间、轮询次数和自身 RECHECK 记录不作为触发证据。固定历史文件可用于回放，不能冒充将来会更新的收件入口。

`next_check_at` 是程序下一次可检查的时间，`deadline_at` 是已约定需要处置的截止。程序可以每分钟读取，但只有实质指纹变化或截止到达才预留提醒意图。同证据不会重复唤醒模型；来源缺失或不可读保留原因，到约定截止仍提醒协调员处置。扫描按页继续，首项等待证据不阻止独立项目。真实接收人、可验证通道、等待事件、承诺与到期动作仍须由协调员沿原任务落实，增加字段不代表对方已接单。

处理提醒的 `record` 应保留提醒内的 `action_id`。同一动作的迟到原生回执只对账该动作；已过期的同动作 `RECHECK` 检查时间仍可入账为到期项。`RECHECK` 消耗当时预留的证据指纹，保留之后新到的证据，下一程序检查不会晚于仍有效的原截止。截止已处置后不自动续期，确有新的约定才附新的 `deadline_at`。明确原生发送前拒绝记为 `NOT_SENT`，发送后失联或结果不明保留 `UNKNOWN`；两者均不消耗证据。原生 `agent_blocked` 的判别依据见[投递适配器](../scripts/herdr_role_contact.py)，自动程序不通过终端输入绕过等待中的批准或问题界面。

协调员读待办和定位现任负责人时，用**当前观察器同一发布目录**内的工具。Mac 可从已加载的 `~/Library/LaunchAgents/io.projectcoordinator.waits.plist` 的 `ProgramArguments` 找到脚本目录。仅看到提醒或 GitHub 评论不结单，保留原项目的生产授权、唯一写者与验收责任。逾期但已送达的提醒仍在未结列表；下一次提醒须有明确复查决定。

**安装与恢复。** 固定发布包含[收件器](../scripts/coordinator_followup_intake.py)和[原生提醒程序](../scripts/coordinator_followup_wake.py)。维护者先用 `coordinator_followup_intake.py bind-source --root "$APP" --transcript "$ORIGINAL"` 绑定已核的协调员原线程文件；首次从启用位置起读，再次绑定同一文件保留游标。只消费该原线程中新产生的显式动作。以前的未结事项由协调员按原回执补登。随后在原 Herdr 会话的专用空闲 shell 前台运行以下命令：

```sh
python3 -I -B "$RELEASE/scripts/coordinator_followup_wake.py" watch --root "$APP"
```

程序每 60 秒处理一次。它核实自己的真实 Herdr 窗格、协调员身份与前台状态，只向空闲的原协调员发内部提醒。登记和提醒不向负责人派生产。独占锁拒绝第二个运行者；发送前记录意图，回执不明时保留原动作。宿主或专用窗格退出后，由维护者在原生宿主恢复该命令，沿旧游标和台账继续。更换原线程或日志文件时先核任命与未决动作。回滚时先正常停止专用前台程序，再按下文回切观察器，保留待办表、来源游标和原生回执。

### 升级、恢复和回滚

1. 暂停新准入与外部发送，核现有动作／写者和已发布结果。已加载的本机定时器用 `launchctl bootout "gui/$(id -u)/io.projectcoordinator.waits"` 停止；该命令只停等待观察器，须分别确认实际调用端与发送端已停写。保存 SQLite 一致性备份、各项目最高代次和未决关联到已批准的私有落点。
2. 用新固定提交安装另一版本目录，在私有副本先运行 `tick` 和状态查询，核旧请求、代次和事件可读，再切换观察器。`recover` 是停止原发送者后的显式恢复动作，需输入 `evidence_ref`，将未定意图转入 UNKNOWN，继续对账原生动作。
3. 回滚时先停止新版，核旧版与当前数据结构兼容，把登录 plist 换回已验证版本并从该文件重新加载。首次安装需要撤回时，卸载该 label，将其登录 plist 移入私有备份目录，保留台账与收据。若需恢复旧数据，先对照原生动作和已知最高代次。尚不能对齐时只做只读检查。

带证据触发的未结待办不能直接交旧版 watcher 运行。旧版会把它们视为纯时间提醒，重新产生无材料唤醒。此类回滚先停原生 watcher，保留原台账、动作和游标，沿原协调员核清未决项并安排明确接续；不得用删除字段或恢复旧数据库抹去已发动作。旧格式条目仍可由新版恢复，固定发布须覆盖实际入口及全部导入文件。
