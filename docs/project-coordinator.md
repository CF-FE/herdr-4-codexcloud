# G8 常驻项目联络与跟进方案

v0.2 · 2026-11-03 · **P0 端点核对进行中，本机协调核心与隔离联调已实现**。首个业务交付对象是凡人项目的一次只读阻塞查询。第 1–6 节是目标合同，实际实现、接入条件和运行步骤在[本机交付与运行](#7-本机交付与运行)。

## 1. 建议与取舍

在已约定持续在线的 Mac 上设置一个可恢复的**协调入口**。G8 向它提交请求，获得固定编号。协调入口负责找对人、拿回答复、追到下一责任人，并把结果交回原 G8。项目负责人保留业务决定和验收权。普通状态跟进由确定性程序承担，需要判断时才联系获授权的负责人或执行者。

| v0.1 中值得保留的目标 | 实际矛盾 | v0.2 的选择 |
| --- | --- | --- |
| G8 可以一直找到协调员 | 常驻模型在线也会丢失会话、任职关系和上次等待条件 | 常驻的是逻辑地址、请求台账与恢复触发器。模型按需参与，重启后按原请求继续 |
| 主动找到实际负责人 | 进程、岗位模板、Issue 写者、历史任命分别证明不同事实。凡人已经有专职负责人受理记录 | 优先恢复已有任职的联系地址。核查任职、验证本次答复来源、确认接手分别留证 |
| 主动解决阻塞 | 查询生成进度、安排听检、重新合成音频需要不同权限。一个通用“处理任务”操作很容易越界 | 首版只开放 `QUERY_BLOCKER`。需要措施时记录责任、条件和现有授权，负责人据此处理。执行或新增授权有独立动作和凭据 |
| 跨项目可靠联系 | 相同账号的 Mailbox 客户端能填写相同 sender 或 recipient。角色名和摘要不能识别 G8 或负责人 | 请求和答复都绑定可验证的原生主体。按主体、项目、动作分别授权读取、提交、报告和确认 |
| 负责人缺失时补位 | 联系失败时旧负责人可能仍在生产，并持有写权 | 失联进入恢复分支。只有任命权威确认空缺、原写权已处理且有明确授权，才进入创建分支 |

若已有受控直连端点，首轮就复用它。直连解决一次投递，协调入口承担 G8 离线、请求超时或负责人换任后的持续跟进。若现场已有入口同时满足寻址、持久跟进和原请求读回，可沿它扩展同一合同，省去另起服务。

## 3. 谁维护什么

需要评审的架构变更（`ARCHITECTURE_GATE`）是新增跨项目请求的跟进责任，以及桥向已认证的本机协调入口交付完整请求／接收结果的合同。现有执行适配器的通过范围是单项目显式调用，新的权限及交付合同处于提议状态。

| 所在位置 | 唯一负责的事实与动作 |
| --- | --- |
| G8 及有效任命方 | 给出业务目标和已有授权范围，接收结果，处理确需公子决定的事项。每个请求固定一个可验证的 G8 调用端及读回方式 |
| Mac 协调入口，本协作仓拟维护 | 维护项目路由、经核验的任职引用与代次、请求和动作台账、等待条件、通知去重。用显式项目 ID 查找准确通道，联系负责人并收回证据 |
| Task Mailbox／Mac 桥，服务仓维护 | 维护传输、认证、原 job／event／结果版本和 collector。需要的本机交付与结果入队扩展由该仓定义，按版本化接口与协调入口交换数据 |
| 凡人或其他项目 | 原正式记录拥有任命依据、业务进度和验收决定。负责人组织执行、核对原件、指定下一步。执行者对其实际执行与产物负责 |
| 原生联系／执行端 | 验证实际接收目标、允许动作、代次和效果。项目已有的联系通道优先。需要 Herdr 时固定真实 session／pane／Agent、目录、有效环境和调用预算 |

首版只需一个本地状态库、一位运行写者和一个状态 CLI。项目目录保存 `project_id`、仓库／原看板引用、任职来源与版本、负责人主体、受控联系地址、允许的运行环境与动作、报告路由、原在途引用及交接点。私密地址和凭据引用留在受限配置。业务进度从原项目读取，协调台账只保存与本次请求相关的事实及来源。

### 可信入口与传输

拟采用的首轮路径如下，去程与回程共用 G8 保存的原 job。

```text
去程   G8 → Task Mailbox → Mac 桥 → 协调入口 → 已验证的原生联系通道 → 项目负责人
回程   负责人答复 → 协调入口核任职、版本和证据 → 原桥补传 → 原 job 的结果版本 → G8 实际读回
```

1. G8 原生端提供实际主体或可验证的授权证明。协调入口核对其绑定、项目、动作、期限和预算，然后接单。答复也要通过已绑定负责人端核验。任意客户端可填写的名称、`whoami` 的共享账号和同一明文信箱里可读的 nonce，单独均不足以证明角色。
2. 能复用既有受信原生通道时，沿该通道验证双方。若只剩共享账号，先做不含私密业务内容的连通预检，状态记为身份待绑定。正式多主体访问须由实际服务入口实现受信主体与项目权限，覆盖已知 job ID 的直接读取、报告、取消和 ACK。消息签名只解决来源，跨项目保密还需要读取控制。新增凭据或持久权限单独核准。
3. 保留原桥的唯一 collector、OAuth 所有权和远端游标。拟增两个受限本机能力，分别交付“按原 job 取回并核过摘要的完整请求”和“按原 event 入队的协调结果”。本机接口也要校验调用者及项目范围。协调入口持久受理后再确认交付，桥可重交同一记录。协调服务有独立生产者身份，不能借用某个 Codex 会话的 Stop 来触发出件。
4. 对 G8 暴露四个逻辑操作，即提交请求、查询进展、读取指定结果和查询健康。优先沿现有获准传输表达，状态／健康查询返回带观察时间的快照。G8 保存原 `job_id`，按它读回明确的版本和摘要。现有事件筛选沿原任务的收件人，监听 G8 别名不足以找到它发给协调员的请求结果。G8 可用时主动拉取，自动唤醒能力另行取证。[事件筛选与结果读取](https://github.com/CF-FE/task-mailbox-mcp/blob/6179582aa7253016a96e3036ba031fd614e29ecb/mailbox_store.py#L256-L341)

### 请求、答复和等待

幂等记录以“经验证的发送方、项目、动作类型、幂等键”联合定位。在授权检查后比较规范化输入摘要，包括目标代次和期限。同键同内容找回原请求，同键异内容拒绝并保留原件，避免他项目探测到既有记录。

| 对象 | 最小记录 |
| --- | --- |
| 联系请求 | schema 版本、项目、`request_id`、原 `task_ref`、关联 ID、幂等键、`QUERY_BLOCKER`、目标任职版本、经验证的发送方、授权引用、期限、预算与证据引用 |
| 联系动作 | `action_id`、原生目标、预期代次、输入摘要、发前意图、实际提交／收件／回复凭据与发生时间。每次外部动作有一个执行者 |
| 负责人答复 | 原项目／请求／动作、答复主体及代次、观察时间、阻塞与影响、证据位置、已核与未核项、下一责任人和触发条件。识别到迟到的旧代答复时，附回原请求供对账 |
| G8 交付 | 原 job、结果版本与摘要、指定 G8 实际读取凭据、G8 提取的阻塞和下一步。需要通知时按请求、实质状态变化和接收者去重 |
| 任何等待 | 跟进责任仍属协调入口，另记当前动作责任人、等待原因、最后证据、下次检查时间或事件、截止预算和升级对象。超过约定时间带着原关联升级，继续保留未决项 |

传输分别记录持久化、提交到通道、目标确认收件和精确结果读取。协调分别记录核验任职、等待答复、需要决策、答复已交付。执行保留原生状态、已发生效果及 `UNKNOWN`。验收分别记录技术验证、独立质量复核和负责人决定。协调员可把“阻塞查询已答复”交给 G8，同时让原生产任务继续等待听检。

Mac 启动时由宿主服务管理器恢复唯一受理实例，读取到期或收到新证据的等待项。查询、补传使用原 ID，并受持久化的次数与时间预算约束。状态 CLI 显示最近成功收件、最近失败、队列与最老等待项、负责人最后响应和下一检查点。协调员无法查询宿主时保留最后观察时间，G8 可以识别过期快照。

失败按证据分类。权威登记确认空缺记“无负责人”，查不到受控登记记“任职未知”。身份不符拒收并留证。认证／路由故障记“通道不可用”，只有原生端明确报告离线才记“离线”。已知请求未受理可在原预算内恢复。可能已投递而失去回执记 `UNKNOWN`，沿原动作对账。只有绑定负责人明确确认收件，才能记“已收未答”。取消请求立即阻止新动作，实际停止、既有结果和写权分别核对。

## 4. 负责人创建与换任

P1 支持发现、核现任、恢复联系和获得答复。生产侧真实缺位才启用 P2，独立测试项目可预先验证 P2 的并发与接管。

1. 查原任命记录、既有实例、未决创建、在途任务、写者及持有的资产。区分已任职但失联、任职证据不足、已确认空缺。
2. 有效任命方选恢复、绑定或创建。创建前先在唯一权威处原子登记项目、预期代次、创建意图和准确预算。两进程竞争只能有一个胜者。原生创建确已发生与否不明时，围绕原动作查找实例。
3. 候选实例验证身份、项目、能力和真实双向联系。向其交接目标、资产、在途生产、审批、未决效果与下一检查点，保留原写者释放或明确拆分范围的证据。候选明确接手后，权威端以原代次为条件激活唯一新任。
4. 各端把有副作用的请求交给唯一权威准入。动作所有者在最终可控的派发／写入点校验 `expected_generation`、动作 ID 与当前权限。切换时停止旧代新增动作，已在外部受理或效果未知的动作仍占用原资源，直至对账。旧端能绕过该入口写生产资产时，先隔离旧写通道或维持只读，跨机隔离验收保持未通过。数据库事务与外部 Herdr 调用之间的窗口由持久意图、原生回读和 `UNKNOWN` 承接。
5. 重启恢复路由、代次、未决动作、游标、已产生结果及待通知事件。结果已生成但确认丢失，先查原版本／摘要，必要时同 ID 补传。旧快照恢复时先核最高已知代次和在途效果，不能证明安全时只读启动，防止复活旧任。

## 5. 凡人首轮如何验

**请求内容**　“请先核对现场所称的 22 段与 Issue 中的‘1 段已读回、21 段已提交’，分别属于哪个批次、输入版本和观察时点。能对应的按已生成、待技术读回、待听检分组，暂时无法对应的保留各自计数。请据此指出当前阻塞、下一责任人、检查条件及证据引用。”范围是查询、联系和读回，额外音频生成次数及生产资产写入次数均为 **0**。

1. G8 从自己的获准入口提交，保存原请求与 job。协调入口登记跟进责任，沿项目导航找到 Project #5、生产 Issue #2 和受控任职索引。优先核历史负责人，不能从看板条目或正在工作的进程推定新任职。[项目入口](https://github.com/CF-FE/fanren-work/issues/9)
2. 在获准联系通道定向发送查询，核负责人本次收件或直接取得其关联答复。若生产 pane 正忙，走既有独立联系通道或排队等待。采用只读工具与最小环境变量白名单，隔离生产命令、写凭据和输出目录。模型提示词中的约束不能替代执行端的权限控制。
3. 负责人沿原执行引用、批次、产物清单、进程／锁、待批事项及回传状态定位阻塞。每项结论注明来源和时间。可只交受控清单引用及分组计数，私人音频留在原宿主。暂时只能核一段时，明确余下的观察缺口。[生产记录](https://github.com/CF-FE/fanren-work/issues/2)
4. G8 读全原请求对应的精确结果，核版本和摘要，并能向公子报告“阻塞是什么、谁接手、下一次看什么”。至此验收**联络闭环**。若阻塞是听检尚无人承接，协调入口继续跟踪项目负责人安排独立听检，取得接手和后续处理证据。由当前生效代次的负责人核实约定的解除条件后，另记**解阻闭环**。例如安排短缺可用合格审查者实际接手为证，音质待验则需实际听检结果。正式整集验收继续遵循凡人项目标准。

若 P0 无法取得历史负责人的现行受控地址，交付项是一个可继续跟进的阻塞记录，包含缺失证据、保管方、已查范围、下一检查点和 G8 的读取凭据。联络成功、负责人空缺和重新生产三项均不能据此成立。

## 6. 分阶段验收与交付

| 阶段 | 最小交付 | 放行依据 |
| --- | --- | --- |
| P0　证实两端地址 | 从原任命方／受控索引核 G8、凡人现任和各自真实入口，确认谁有权联系、谁能读结果、哪些证据可在该通道传递 | 形成经权威确认的绑定与权限范围，或列明具体缺口、保管方和解锁条件。账号共享而缺可靠归因时，只做连通预检 |

### 安装、启动和查看

在本仓选择已审阅的完整提交作为 `REV`。用原有 Python 3.10+ 运行。安装需要当前用户可写的目录。每个发布目录保留固定源码与解释器路径，共用的 `state` 保留台账。首次安装默认没有生产项目绑定。

```bash
REV=$(git rev-parse HEAD)
APP="$HOME/Library/Application Support/ProjectCoordinator"
python3 scripts/install_project_coordinator.py --revision "$REV" --destination "$APP"
RELEASE="$APP/releases/$REV"
plutil -lint "$RELEASE/observer.plist"
python3 -I -B "$RELEASE/scripts/project_coordinator.py" --state-dir "$APP/state" tick
```

需要在当前 Mac 登录会话启用本地定时检查时，运行 `launchctl bootstrap "gui/$(id -u)" "$RELEASE/observer.plist"`。用 `launchctl print "gui/$(id -u)/io.projectcoordinator.waits"` 核注册和实际退出状态。配置为 RunAtLoad 及每 60 秒执行一次，单轮最多 25 项到期等待。每个等待版本的检查点与截止升级分别持久化、去重。是否实际联系负责人和 G8 是否读取，查各自回执。需要跨登录自动加载时，另按宿主用户级 LaunchAgents 安装约定持久登记并验证重新登录。

项目登记使用受信本机 `register_project` 操作和私有 JSON 输入，字段为 `project_id, repository, project_ref, g8_principal, report_route`。只有在任命、来源验证、交接和旧写权四类证据齐全时才执行 `activate_owner`。该操作同时要求 `expected_generation, owner_principal, endpoint, appointment_ref, verification_ref, handoff_ref, release_ref` 及项目 ID。负责人创建操作登记经授权的原生意图与回读，实际创建依赖经授权的生命周期入口。业务消息里的“任命”文本没有这些权限。

例如，用只含 `project_id` 的私有文件运行 `health`，增加 `request_id` 则可运行 `inspect`。`events` 与 `notifications` 支持 `after` 和 `limit` 分页。四种查看均通过本地库读取，实际 G8 读回需独立的原生凭据。

```bash
python3 -I -B "$RELEASE/scripts/project_coordinator.py" --state-dir "$APP/state" health --input "$PROJECT_LOOKUP"
python3 -I -B "$RELEASE/scripts/project_coordinator.py" --state-dir "$APP/state" inspect --input "$REQUEST_LOOKUP"
```

### 升级、恢复和回滚

1. 暂停新准入与外部发送，核现有动作／写者和已发布结果。已加载的本机定时器用 `launchctl bootout "gui/$(id -u)/io.projectcoordinator.waits"` 停止。保存 SQLite 一致性备份、各项目最高代次和未决关联到已批准的私有落点。
2. 用新固定提交安装另一版本目录，在私有副本先运行 `tick` 和状态查询，核旧请求、代次和事件可读，再切换观察器。`recover` 是停止原发送者后的显式恢复动作，需输入 `evidence_ref`，将未定意图转入 UNKNOWN，继续对账原生动作。
3. 回滚时先停止新版，核旧版与当前数据结构兼容，再用原发布目录的 plist 启动本机观察器。若需恢复旧备份，必须先对照原生动作和已知最高代次，避免复活旧写权。尚不能对齐时只做只读检查。
