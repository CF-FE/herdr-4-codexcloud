# 云端Dot、项目协调层与 Cloud 路由协作约定

版本 1.6 · 2026-11-04。本文维护本组织的决策、路由和交接规则。分层与回收路径见[全局架构图](architecture.md#整套协作分工)，通用岗位定义见[组织技能](../skill/organization-collaboration/SKILL.md)，实际部署见[状态页](status.md)。

主动汇报、暴露并逐级冒泡问题与风险是**全局协作责任**，适用于全部项目、协调层和执行层的所有角色，凡人仅是边界示例。通用权威条款维护在组织技能的[共同边界](../skill/organization-collaboration/SKILL.md#共同边界)与[共同汇报规则](../skill/organization-collaboration/references/context-and-reporting.md#回报与证据)；本页明确本组织的默认责任链，不以角色模板或通道尚未自动化免除报告与承接义务。

## 全局角色名称映射

本组织统一称 **云端Dot**。历史材料中的“G8”和“云端 Dot”均指这个与用户沟通的云端助手角色。各项目的文档、任务包和汇报沿用同一参与者关联，避免重复任命、派发或汇报。

Worker、项目负责人和协调员仍是各自角色，不能因读取本规则自认云端Dot。名称映射不合并不同系统的原生ID或凭据，不代替实际身份、权限和通道验证；历史名称保留原引用，按同一角色解释，不批量改写运行台账或在途记录。

## 1. 默认分工与取舍

Super-Agent 对公子提供一个需求与决策入口，下游分为项目协调和 Worker 执行两层。公子与云端Dot共同明确目标。云端Dot验证需求假设、发起委派、回收进展并主动汇报，**项目和非项目交付均不得由云端Dot自行验收**。项目默认由现任项目负责人验收。另指定验收者时，在原任务写明对象和验收范围。非项目成果须在交办时明确另一位验收者。验收者作出通过、返工或放行决定，云端Dot可确认自己的交办、读取和汇报动作已经完成。

| 岗位 | 决定和交付 | 何时找上游 |
| --- | --- | --- |
| 公子／用户 | 确定总体目标和授权，决定超出既定范围的取舍 | 云端Dot将需要用户决定的问题连同影响、选项一起提报 |
| 云端Dot | 调研需求，验证假设，按成果拆任务，确定依赖、下游归属和验收标准，指派验收者 | 从信箱或看板回收进展，主动向公子汇报里程碑、风险和结果。需改变目标或新增授权时，带影响和选项提请公子决定 |
| 项目协调员 | 找到现任负责人并交付目标，跟踪承接和结果，协调跨项目资源。在授权内直接解决依赖，也可承接独立的非项目任务 | 向云端Dot汇总约定里程碑、重要风险或超出授权的取舍 |
| 项目负责人 | 拆解项目内工作，选择并联系执行者和独立审查者，确定范围与交期，安排整改和复核，默认承担验收；另有指定时向该验收者交付 | 向协调员报告关键成果、影响项目承诺的风险及需要协助解决的依赖 |
| Worker | 按绑定的任务、宿主和权限实施，交付可定位版本、产物、自检结果及未验项 | 向直接负责人回报进展和影响交付的阻塞 |
| 独立审查者／流程审计者 | 审查者核指定版本的质量，审计者按需核验责任、处置过程和证据 | 按原任务报告发现，由指定验收者作业务决定 |

**凡人听检。** 负责人已采纳首批 22 段原音候选。可选人工听审按[成品人工介入清单](../skill/organization-collaboration/references/context-and-reporting.md#成品人工介入清单)办理。公子可按自己的时间听，疑点记在片段旁，整批听完勾一次。负责人据反馈处置并决定验收。云端Dot可从原项目获知实质进展。[本批清单](https://github.com/CF-FE/fanren-work/issues/2#issuecomment-6625500276)

Mac 接手后，项目负责人在授权范围内推进。云端暂时离线时，本地保存进展和验收结论，恢复连接后按原任务补传。云端Dot通过既有定时查信或项目看板获知实质变化并主动向公子汇报。

### 项目主仓与项目级规范

正式项目默认在 `CF-FE` 绑定一个主仓。现任负责人按[岗位规范](../skill/organization-collaboration/references/project-owner.md#项目主仓与项目级规范)复用或创建主仓，协调员处理项目归属冲突和权限缺口。首次纳入协调层时，由有登记权限的人绑定已核实的仓库，负责人在原 Project／Issue 留入口。关联组件可沿用各自仓库，由主仓列出用途和链接。

**项目级规范由负责人在主仓制定和维护。** 优先沿用已有的规范入口。仓库根 `AGENTS.md` 可放执行者开工前必读的约定，README 链到具体文档。项目可在既定目标和授权内细化工作方法、产物格式、质量标准、验收证据及交接办法。代码、项目文档、Skill、插件与配置模板按实际需要归档。影响在途任务的修订要注明适用版本和切换点，由负责人告知受影响的执行者及验收者。涉及其他项目的共同约定由协调员找相应维护者对齐，涉及公子已定的目标、验收条件或新增授权则沿原任务取得决定。

例如，凡人旁白的术语读音、听检方法和交付格式属于凡人主仓。哪一批待听、谁跟进、哪一版已验收，记在凡人的原 Project／Issue。Win 上哪种模型已验证能听辨，记在[组织环境能力看板](https://github.com/orgs/CF-FE/projects/6/views/3)。

### 云端Dot作为发起者

完整目标默认沿 **云端Dot → 项目协调员 → 现任项目负责人 → Worker** 交办。独立小迭代按[直派条件](#3-云端dot小迭代直派)办理，仍保留项目归属、唯一派发者和指定验收者。协调层可选择 Mac、Win 或获准的 Cloud 路线。Mac Worker 在本地 Herdr 受理，Win Worker 通过 Herdr 保存的机器配置经 SSH 定向受理，Codex 路由创建的 Cloud 作业按其原生任务 ID 回收。[岗位与宿主](agent-hosts.md)

- **交办前做到可开工。** 明确用户要的结果、验收标准、授权和预算。优先验证一旦判断错就会改变目标、成本或路线的假设。只能到现场确认的细节，交给最接近事实的人在执行中解决。
- **按成果拆分。** 每个能独立交付的成果带上原任务引用、负责项目、依赖和验收者。项目协调层确认谁承接、协调跨项目资源；项目负责人决定具体步骤、人员和排期。无需把每一步做成云端子任务。
- **接手后在本地闭环。** 协调层受理前，云端Dot沿原引用跟进投递；受理后，由协调员跟到负责人明确接手。此后项目负责人承担项目内跟进，协调员处理跨项目依赖。预算内可逆工作直接推进。确需改变目标、扩大权限或作跨项目取舍时，在原任务写明所需决定、影响和可继续的工作，由云端Dot提报。新决定再沿同一任务向下交付。

凡人这单，云端Dot明确“用已有 22 段取得独立听检结果”，给出批次及质量标准；谁来听、怎么分段、何时交首份回执和如何处理问题，由凡人负责人决定。

### 弱连接下的进度与迭代

| 云端Dot想知道什么 | 入口 | 更新责任 |
| --- | --- | --- |
| 这一单有没有接手，最近的答复或阻塞是什么 | Task Mailbox。按原 `job_id` 查最新结果版本、观察时间和证据引用 | 协调员将负责人摘要送入 Mac 原发件队列，桥联网后补传 |
| 整个项目到了哪一步，谁负责，是否已验收 | GitHub Project 的原条目及其关联 Issue | 项目负责人或获授权的记录者回填里程碑和验收结论 |

两处保留同一 Issue／条目引用。云端Dot回收有任务号的进展时看结果版本与观察时间；回收项目成果时看 Project 所关联的验收记录。仅走项目原入口的任务无需补造信箱单。信箱里较新的进展可先用，项目最终质量结论沿指定验收者的原始验收记录核对。落板失败待同步即可。无需等待两个入口同时更新，也无需将每份分段回执各抄两遍。

例如，Worker 已交付一批素材，负责人只验收了素材接收。原 Issue 可以登记“素材接收通过，整集待验”，云端Dot据此汇报这一里程碑。信箱或平台显示已完成的回执，只按它实际覆盖的任务解释。

### 协调员转交与待回填

收到「转给现任负责人」的委派，协调员复用原项目、有效任职代次和联系编号，沿登记的 Herdr 会话直接转交。要求回执时，收回对方在原线程对本条消息的答复。投递结果未知时先对原回合核账。普通联络只需要核对目标角色和本次消息，私人目录等资料沿原私有通道交给指定接收者。

负责人会话退出时，先按已登记的线程 ID 核对在途回合和占用。能安全恢复时，在真实 Herdr 里沿同一线程、工作目录与已有权限恢复，核实身份后继续原联系。只有任命冲突、有效权限不足，或并发占用无法核清时，才暂停受影响的动作并说明所需决定。协调员负责后续跟进。[协调员岗位](../skill/organization-collaboration/references/project-coordinator.md)

GitHub 回填与接单分开。协调员先把原 Issue、可公开摘要、依据和记录键保存到本机，由获授权的记录者在独立执行通道处理。可能弹出确认的 GitHub 写操作一律走该通道。需要批准时只挂起对应评论，协调员继续收件、联系负责人和回收结果。恢复写入前先核原调用和原 Issue，已有评论就取回链接，结果仍未知时保留待核状态。[安装与操作](project-coordinator.md#nonblocking-contact)

### 动态信息由谁维护

同一事实只维护一处。需要别人决策或跟进时，在原 Project／Issue 留摘要和证据引用；时点不一致时注明各自的观察时间。按实质变化更新，不要求定期抄表。

| 什么会变 | 原记录与更新者 | 何时更新或核对 |
| --- | --- | --- |
| 环境、工具、模型和可承接的工作 | 宿主维护者提供证据，协调员或获授权的记录者更新 [CF-FE 环境能力](https://github.com/orgs/CF-FE/projects/6/views/3)原卡；每个实际环境一张 | 新环境接入、安装、升级、实测、降级或退役时，写明版本、适用范围、观察日期与证据。将来接入 Linux 直接加卡；调用合同或离线模板改变才改仓库 |
| 负责人、代理、交接和当前写者 | 有效任命、协调员的身份与代次绑定、原生接手和写权交还记录；项目条目给可联系的岗位与交接引用 | 任命、代理、换任或交还时更新。改看板经办人不会任命 Agent，也不会转移写权 |
| 排期与项目进展 | 负责人在原项目条目及关联 Issue 维护优先级、里程碑、依赖、阻塞、责任人和下次检查点 | 承诺改变、出现影响或阻塞解除时更新；跨项目调度由协调员跟进。未受影响的工作继续 |
| 产物、复核、验收与发布 | 原件或提交由执行端保存；负责人关联版本，指定验收者在原任务记录通过范围或返工，发布者另记实际部署 | 交付新版本、验收或发布结论变化时更新。云端Dot据此汇报，不代签 |
| 单件投递、接手与回传 | 信箱、桥和原生任务分别保存各自回执，协调员按原任务号对账 | 超时或恢复查原单；消息入箱、已读或报告已发布，都不能推出成果通过 |
| 实时容量、在线状态和有效权限 | 派发者在 Herdr／Cloud 原生入口核队列、占用与目标；本单授权、预算、期限、撤权和锁以执行端受控记录为准 | 派发、恢复或写入前按本单核。只有持续降级或影响交付时才在看板写影响和跟进人，不抄心跳、凭据或临时授权 |

### 哪些任务适合交协调层

| 选择 | 收益 | 代价与采用边界 |
| --- | --- | --- |
| 项目工作优先由协调层承接 | 保留上下文、统一优先级和写权，减少多头指挥 | 小改也逐层审批会增加等待。完整交办后由协调层自主推进，只回报实质变化与需决定事项 |
| 独立小迭代由云端Dot直接唤起 Codex Cloud | 减少搬运，快速形成可检查成果 | 可能重复派发、遗漏项目影响。仅在第 3 节条件成立时采用，项目归属与验收不随创建者改变 |
| 协调员决定任务，Cloud 路由负责原生调用 | 让协调层可统一选择机器或云端，云端Dot无须逐次转手 | 需要真实工具、权限、执行关联和回报合同。当前属于目标设计，须按第 4 节验证后才能声称打通 |

“尽量不越级”保留必要技术核查、已授权代建和小迭代例外；这些沟通不形成第二派发入口。紧急、失联、工具可见、改动行数少，都不能单独证明可以越过现任负责人、写者或权限边界。

## 2. 以完整成果交办

同一目标保持一个父任务和一个当前派发／续发协调者。云端Dot交清以下内容；已有正式记录直接引用，不重复建单或逐字段询问用户：

| 内容 | 最少说明 |
| --- | --- |
| 目标与预期 | 要解决的问题、可检查的终点、优先级及验收标准 |
| 输入与边界 | 固定版本、依赖、允许修改的资产、不做范围和生产限制 |
| 授权与预算 | 有效授权来源、允许动作、资源／时间预算、停止条件 |
| 责任与回报 | 原正式任务、业务负责人、唯一派发者、当前写者、验收者、真实通道及无推送时的拉取人和检查点 |

协调层可按项目或跨项目依赖划分交付，由各项目负责人决定项目内的子任务和实施顺序；不把“调研→改一处→跑一条命令→回报”变成云端Dot反复转交的任务链。需要新业务决定、越界、跨项目冲突或预算取舍时，带着影响、证据和可选方案集中反馈。子任务与父目标保留关联，不把一个大目标拆成许多“小任务”取得直派资格。

### 协调员的有界主动性

协调员接手后，在云端Dot交付的目标、权限、资源和停止条件内，可以主动核对风险与依赖、追踪未完成事项、联系已绑定负责人、推动已授权且就绪的工作、调整不改变既定承诺的调度顺序，并提出改进。无需等待云端Dot逐项催办；有现行授权的普通调度可直接实施，改进建议是否执行仍按实际影响判断。

| 影响 | 自主行动与升级 |
| --- | --- |
| 目标和承诺不变、依赖明确、预算内、可逆且无冲突 | 在实际工具权限内主动推进，保留决定理由和执行／结果引用；无实质变化不重复通知 |
| 可能改变交付承诺、验收口径、已定跨项目优先级，或影响共享写权、重要资源预留 | 先核影响及已有授权；已有授权明确覆盖时按约定实施并及时回报，否则在相关新动作前交云端Dot决定，必要时由云端Dot向用户提报 |
| 新目标、新权限、超预算、生产／部署扩展，或原执行 UNKNOWN | 只继续独立获准工作；提交具体方案、影响、回退及所需决定。UNKNOWN 沿原执行对账，不用主动性作重派理由 |

在原任务记录“触发事实与证据 → 决定、理由及所据授权 → 实际动作与原生引用 → 结果、影响和下一责任人”。提议、已决定、已执行和已验证分开，回报按成果或实质变化合并。到检查点后按原关联推进或升级，预算到期则交清未决项；没有真实调度／唤醒入口时只约定由谁在何条件下复查，不声称自动巡检、持续在线模型或无人值守执行已经实现。

### 主动汇报与用户沟通

**协调层与执行层所有角色都有主动汇报义务，问题与风险应及时向已绑定的上游暴露，不等待反复追问。** 接手时约定关键节点、最迟复查点、真实回报通道和读取责任；这些是跟进约定，不默认新增定时器或高频心跳。

| 报告方 | 默认接收者与责任 |
| --- | --- |
| 所有 Worker（包括实施、研究、审查及其他专业角色） | 向任务绑定的直接负责人报告成果、检查、问题与风险；由负责人向协调员汇总。若绑定Cloud路由为回报中转，须记录最终接收者，路由已读不能冒充负责人已读 |
| 项目负责人 | 向项目协调员报告项目进展、质量／验收、资源依赖与风险；协调员据此统筹，负责人继续承担业务责任 |
| Cloud 路由执行者 | 向发出调度决定的协调员报告受理、原生引用、执行异常和产物；云端Dot直派时向云端Dot报告，项目成果交原负责人集成，按原任务的验收者安排验收 |
| 项目协调员 | 将关键进展、决定和需要上游取舍的事项更新到原信箱或项目记录，供云端Dot回收，并推动未完成事项 |
| 云端Dot | 对公子负有主动汇报职责。通过任一入口发现里程碑达成、首份业务回执、交期变化或重要阻塞时，应向公子说明进展、影响和下一步。两处出现同一进展只报一次 |

任务已有有效汇报绑定时沿原记录。关键成果、风险、阻塞、重要决定及交付承诺变化，向绑定的上游报告影响、证据和下一步。普通进展可合并，按约定检查点跟进。取消或退出时交清未决动作、下一责任人和写权交还情况。需要他人处置的事项由报告方跟进到明确接手。无推送能力时先确定谁来读取，接收方说明是否承接及下次检查条件。

项目阻塞默认沿 **Worker → 对口项目负责人 → 项目协调员 → 云端Dot → 公子** 升级。Worker 先报告影响，同时处理本岗位权限内的问题。负责人解决项目内依赖，协调员处理跨项目资源与冲突。云端Dot在已有授权内协调，只有需要公子取舍或新增授权时才提请决定。上游失联或风险紧急时按原任务约定及时升级。发生效果未知时沿原派发记录核对，独立且已具备条件的工作继续。

### 权限内就地解决，方案和结果继续向上报告

**任一层能在自身权限内解决，就在该层接手并闭环；不把可解决的问题继续上推。** 这适用于所有Worker、Cloud路由、项目负责人、协调员与云端Dot。先核授权、输入、预算、当前写者和验证条件，复用原问题与执行引用；按[就地处置规则](../skill/organization-collaboration/references/context-and-reporting.md#权限内解决与向上汇报)区分方案、行动、缓解、验证解决和正式验收。处理者仍主动向已绑定上游交方案、实际结果、验证证据和剩余影响，普通事项可合并汇报。

拦截解决责任不能拦截风险信息。重大紧急安全风险、重要交付／跨项目影响和用户必须决策的事项及时预警；已有授权的应急处置可并行，不能以“正在处理／已经缓解”隐瞒、延迟升级或替用户作决定。自身无权解决或预算／条件不足时，带已做工作和需决定项升级，原责任保持到明确承接。

**GitHub Project 保留项目状态，关联的原 Issue 保留问题经过。** 负责人或授权记录者沿同一条目更新“发现时间、事实与影响 → 已做处置、当前责任人和下一检查条件 → 升级给谁、决定及依据 → 结果、解除证据和未结事项”。已缓解、已解除和成果已验收分别记录。公开位置只放适合披露的摘要。写入失败时保留待同步记录，先处置或预警，恢复后补写并回读。[问题处置记录](../skill/organization-collaboration/references/task-traceability.md#问题处置闭环记录)

本规则不新建Project、不自动迁移原正式入口或扩展访问权限；旧入口到Projects的映射需按既有迁移决定确认。局部问题处理、上游实际读取、Projects同步、业务验收分别记证，解决局部问题不自动关闭父任务。本轮只是规范修订，不声称已经写入某块看板或打通自动汇报／同步。

## 3. 云端Dot小迭代直派

公子已允许云端Dot直接委派独立小迭代。每次沿原任务引用覆盖本次目标、资产和预算的有效授权；已有授权覆盖即可执行，超出部分先交相应授权方决定。直派还须同时满足以下条件。

1. **成果独立**：目标、输入、输出和检查清楚，能形成一个有界交付；不要求协调多个项目的新决定或频繁重新分派。
2. **范围可控**：在已获准仓库／资产内，改动可审查、可撤回；调用、时间和写入范围有界。文档、局部修复、补充验证可以适用，具体仍看影响。
3. **依赖与权限成立**：所需资料、工具和环境实际可用；不隐含新增部署、生产写入、凭据变更、付费许可或超预算动作。现有阶段冻结和生产限制继续适用。
4. **没有冲突**：核原任务、已有分支／PR／Cloud 执行和未决创建；没有另一派发者在做同目标，也不争用原写者、共享接口或资源。不同分支名不自动证明没有语义冲突。
5. **有人收尾**：云端Dot承担这次派发、结果拉取与异常跟进；项目成果交原负责人集成，由本单验收者验收。非项目任务没有默认的项目负责人，发起时由云端Dot指定验收者。

| 情形 | 协调层知情或承接方式 |
| --- | --- |
| 无项目实施影响的独立组织整理／比较 | 云端Dot可直接完成并在原任务合并回报，无需另建协调单 |
| 属于项目、满足上述条件，形成独立候选改动 | 派发前在原任务记录目标、范围、授权依据、唯一派发者和派发意图，并告知现任项目负责人，可经协调员转达。创建受理后补真实 Cloud 引用，交付时由项目负责人收取版本和验证结果 |
| 已绑定项目负责人，通知暂不可达，但独立授权、输入和无冲突证据齐备 | 仅推进不依赖接收者新决定或共享写权的工作；记待送达、云端Dot的跟进责任及检查点。不能把沉默当接受，也不能因此跳过本单验收者的验收 |
| 涉及在途项目计划、共享资产／容量或需要新的项目决定 | 在相关写入或占用前由协调层和负责人安排；等待时可继续独立获准的只读分析 |
| 执行中超出独立性、预算或边界，或需要反复续派 | 停止受影响的新增动作，将原任务、已有产物和未决执行交协调层；其他无依赖工作继续 |

已有有效任务包或长期授权直接复用；缺失的通知、任命或执行回执分别记录，不能为填写完整而编造。派发记录与正式入口规则仍按[任务追溯](../skill/organization-collaboration/references/task-traceability.md#派发与恢复)执行。

## 4. 协调员指挥 Cloud 路由

以下为目标职责合同，**尚不表示现有协调程序能够触发 Codex Cloud**：

| 职责 | 决策与交付 |
| --- | --- |
| 云端Dot | 提供完整目标、优先级、授权和跨项目约束，感知并主动向公子汇报实质进展；需要用户决定时集中提报 |
| 项目协调员 | 在既定目标和授权内统筹各项目负责人、跨项目资源、调度顺序及 Cloud／本地路线；结合负责人审定的业务任务包，在已有预算内安排执行与检查点，指挥 Cloud 路由并跟踪回传，不替代负责人业务验收 |
| Cloud 路由执行者 | 核完整任务包、目标环境和已有执行；承担一次原生创建／获准续发，保存真实引用，拉取状态与产物，沿原任务交回协调员。工具只能回到云端Dot时，云端Dot可作已约定的中转者 |
| Cloud Worker | 在允许范围内实现、自检并交精确版本、证据、未验项和阻塞；不能自行扩大目标或继承其他端权限 |
| 项目负责人 | 决定业务范围与项目取舍，组织独立复核与集成。默认验收并向协调员回报，另有指定时将成果交该验收者决定。 |

“Cloud 路由”是一项执行职责，可以由具备获准原生入口的现有参与者承担，不要求新建服务或常驻角色。每次任务包明确：协调员负责派发决策和跟进，谁是唯一实际调用者（`dispatch_owner`），谁拉取、谁接收、谁验收；另一入口不得并发再建同目标执行。协调员可在既有授权内安排续发，路由执行者须先核原任务状态，不能只因收到重复指令再次创建。

**当前可用边界。** Mac 已部署协调员与桥的完整目标交办版本。`QUERY_BLOCKER` 只处理查询，`DELEGATE_GOAL` 需要该单的可信来源、准入和原生目标。已有 Cloud 环境和 CLI 创建入口，协调员自动创建 Cloud 作业、将成果交回项目负责人的完整路径仍待验证。复用原单和已有准入，协调职责本身不授予 Cloud 执行权限。[部署证据](status.md#当前结论) · [交办合同](goal-handoff.md)

当前项目任务可沿获准通道交云端Dot代建，符合第 3 节条件时也可由云端Dot直派。只有查询入口时，目标包记为待承接。验证协调员路线需核其实际身份与授权、Cloud 原生任务引用、同一任务的产物回收和指定验收者的结论，并核重复请求、创建结果未知及取消后的对账。

## 5. 幂等、异常与移交

用原正式任务引用、成果范围、输入版本和派发意图识别同一工作，关联平台实际返回的任务／回合。它们是对账依据，不宣称 Cloud 服务端提供幂等或恰好一次执行。

| 情况 | 必须采取的动作 |
| --- | --- |
| 同目标同输入已有执行，或重复收到指令 | 复用原引用查状态与产物；不另开任务。改变输入时登记新版本、影响及对旧执行的处理，再决定是否需要新执行 |
| 创建／续发超时、受理不明 | 保留 `UNKNOWN`，原派发者沿原调用对账；一次空列表、无回复或过期快照不能证明未执行，不改入口重派 |
| 原生创建成功，记录回填或结果通知失败 | 保存原生引用、产物和待补写项，补原记录／原结果；不重新运行已成功部分 |
| 权限或环境故障 | 明确失败动作、目标、原因、已发生效果与停止点；原任务内有界排障，交对应维护者。授权缺口由云端Dot汇总给用户，不能复制凭据或换路绕过拒绝 |
| 需要协调层接手 | 交原任务、目标／边界、输入与产物版本、原生执行、当前写者、UNKNOWN、预算余量、待交付结果及下一检查点；收到明确接手回执前，原派发者继续跟进 |
| 取消、撤权或写者切换 | 立即约束相关新动作，沿原执行核停止、已发生效果与写权交还。通知送达、任务取消和进程已停分别留证；旧写者未交还，不放行冲突写入 |

实现问题在原范围和预算内处理；项目范围／依赖／优先级问题交协调层与负责人。既定目标、优先级、授权和预算内的跨项目调度由协调员处理；超出这些边界的取舍、新授权及超预算事项交云端Dot，其中确需用户决定的再集中提报。升级必须带可决策的证据与选项，不能只把整段日志向上搬运。协调员暂不可达时保持原任务与恢复责任，不自动任命新负责人或直派生产。

## 6. 验收、反例与回看

每次交付保留原任务、输入版本、提交／PR／产物引用、检查方法与范围、未验项和下一责任人。原生受理、产物保存、作者自检、所需独立复核、指定验收者的业务决定、结果读回和写权交还分别记证。检查范围与风险相称，沿用原任务约定的必验项。

| 场景 | 路由判断与可检查结果 |
| --- | --- |
| 用户要求整理本仓规范，输入完整且无冲突 | 云端Dot可直派 Cloud 形成草稿 PR；记录验证与未实现能力，合并、部署和项目采用分别由相应决定支持 |
| 局部修复原本独立，后来需改共享协议或多项目接口 | 在扩范围前移交协调层；保留已做补丁和原执行，不能拆成多个小改继续越界 |
| 一行修改即可重发凡人音频 | 改动虽小仍影响生产许可及现任负责人。走项目流程，查询入口不得生成音频 |
| 凡人负责人暂未回复 | [已绑定负责人](project-coordinator.md#可信入口核验p0)的存在不能由一次失联推翻；沿原请求查询／恢复，禁止重复补位与生产派发 |
| 协调员要求 Cloud 修复，但目前只有 `QUERY_BLOCKER` | 目标包记待承接，或沿获准代建路线继续；信箱 ACK 不能证明 Cloud 已创建 |
| Cloud 无回复而协调员提议再建一次 | 保留原任务 UNKNOWN 并对账；只有确认未执行且当前授权仍有效，才按原意图处理未发生动作 |
| 负责人在预算内修复局部问题并完成约定验证 | 本层闭环，向协调员交方案与结果，在原Projects关联任务留痕；父任务验收另核，无需把解决责任继续上推 |
| 协调员能暂时缓解重大安全风险 | 及时向云端Dot预警并采取已授权措施；记录剩余风险与用户需决定事项，不能以“已拦截”为由静默结案 |
| 问题已解决但Projects写入被拒绝或结果未知 | 报告已验证事实及待同步项，拒绝不绕过、UNKNOWN先对账；保留记录责任，不把条目或项目冒称Done |

在原任务按实际证据回看：有效成果、人工转述次数、等待原因、重复派发／冲突、未决项年龄及验收成本。直派若持续产生协调返工，后续同类任务改由协调层承接；协调层若把已授权小改变成逐步审批，缩减重复交接。调整的是受影响范围的规则，不为改善统计把未验改成通过，也不重启在途任务。
