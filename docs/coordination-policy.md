# G8、项目协调层与 Cloud 路由协作约定

版本：1.0 · 2026-11-04。根据公子确认的分工及小迭代直派授权整理。本页维护本组织的决策、路由与交接规则；通用职责见[组织技能](../skill/organization-collaboration/SKILL.md)，协调程序及已有回执见[协调入口](project-coordinator.md)，运行状态见[状态页](status.md)。本页中的 G8 指云端Dot，不新增身份、任命或运行组件。

## 1. 默认分工与取舍

**G8 位于项目协调层上游，主要与用户沟通；向协调层一次交清完整目标、预期与边界，接收反馈和结果，处理跨项目取舍。** 协调层优先联系既有项目负责人，组织拆解、执行与跟进；负责人保留项目业务决定、集成和最终验收。执行者在任务包内自主完成实现步骤。

**项目协调员在项目协调层拥有覆盖面最广的组织调度职责**：在用户与 G8 已定目标、优先级、授权和预算内，统筹各项目负责人、跨项目资源与 Cloud／本地路线，决定调度顺序、协调冲突并跟进结果，不必把日常调度逐项交 G8 批准。项目负责人负责领域拆解、业务质量和验收；超出既定跨项目取舍、预算或授权时再交 G8。组织调度权不等于各系统访问权、任命权、无限预算或代替安全审批，实际调用仍由具备对应工具和权限的一方完成。

| 选择 | 收益 | 代价与采用边界 |
| --- | --- | --- |
| 项目工作优先由协调层承接 | 保留上下文、统一优先级和写权，减少多头指挥 | 小改也逐层审批会增加等待。完整交办后由协调层自主推进，只回报实质变化与需决定事项 |
| 独立小迭代由 G8 直接唤起 Codex Cloud | 减少搬运，快速形成可检查成果 | 可能重复派发、遗漏项目影响。仅在第 3 节条件成立时采用，项目归属与验收不随创建者改变 |
| 协调员决定任务，Cloud 路由负责原生调用 | 让协调层可统一选择机器或云端，G8 无须逐次转手 | 需要真实工具、权限、执行关联和回报合同。当前属于目标设计，须按第 4 节验证后才能声称打通 |

“尽量不越级”保留必要技术核查、已授权代建和小迭代例外；这些沟通不形成第二派发入口。紧急、失联、工具可见、改动行数少，都不能单独证明可以越过现任负责人、写者或权限边界。

## 2. 以完整成果交办

同一目标保持一个父任务和一个当前派发／续发协调者。G8 交清以下内容；已有正式记录直接引用，不重复建单或逐字段询问用户：

| 内容 | 最少说明 |
| --- | --- |
| 目标与预期 | 要解决的问题、可检查的终点、优先级及验收标准 |
| 输入与边界 | 固定版本、依赖、允许修改的资产、不做范围和生产限制 |
| 授权与预算 | 有效授权来源、允许动作、资源／时间预算、停止条件 |
| 责任与回报 | 原正式任务、业务负责人、唯一派发者、当前写者、验收者、真实通道及无推送时的拉取人和检查点 |

协调层可以按独立成果拆分子任务，并在现有授权内调整实现顺序；不把“调研→改一处→跑一条命令→回报”变成 G8 反复转交的任务链。需要新业务决定、越界、跨项目冲突或预算取舍时，带着影响、证据和可选方案集中反馈。子任务与父目标保留关联，不把一个大目标拆成许多“小任务”取得直派资格。

### 协调员的有界主动性

协调员接手后，在 G8 交付的目标、权限、资源和停止条件内，可以主动核对风险与依赖、追踪未完成事项、联系已绑定负责人、推动已授权且就绪的工作、调整不改变既定承诺的调度顺序，并提出改进。无需等待 G8 逐项催办；有现行授权的普通调度可直接实施，改进建议是否执行仍按实际影响判断。

| 影响 | 自主行动与升级 |
| --- | --- |
| 目标和承诺不变、依赖明确、预算内、可逆且无冲突 | 在实际工具权限内主动推进，保留决定理由和执行／结果引用；无实质变化不重复通知 |
| 可能改变交付承诺、验收口径、已定跨项目优先级，或影响共享写权、重要资源预留 | 先核影响及已有授权；已有授权明确覆盖时按约定实施并及时回报，否则在相关新动作前交 G8 决定，必要时由 G8 向用户提报 |
| 新目标、新权限、超预算、生产／部署扩展，或原执行 UNKNOWN | 只继续独立获准工作；提交具体方案、影响、回退及所需决定。UNKNOWN 沿原执行对账，不用主动性作重派理由 |

在原任务记录“触发事实与证据 → 决定、理由及所据授权 → 实际动作与原生引用 → 结果、影响和下一责任人”。提议、已决定、已执行和已验证分开，回报按成果或实质变化合并。到检查点后按原关联推进或升级，预算到期则交清未决项；没有真实调度／唤醒入口时只约定由谁在何条件下复查，不声称自动巡检、持续在线模型或无人值守执行已经实现。

### 主动汇报与用户沟通

**协调员有主动向 G8 汇报的义务，不等待 G8 反复追问。** 接手时约定关键节点、最迟复查点、真实回报通道和读取责任；这些是跟进约定，不默认新增定时器或高频心跳。

| 触发 | 协调员向 G8 交付什么 |
| --- | --- |
| 目标受理、关键结果或实质进展 | 明确接手点，或新成果／阶段变化、精确版本、验证范围和下一步；普通工具调用不逐条播报 |
| 新风险、阻塞、UNKNOWN 或解除条件变化 | 影响范围、证据、已采取措施、可继续项、责任人、解除条件与下次检查点；需决定或可能影响承诺时及时报，不能等总结掩盖 |
| 重要调度决定、范围／资源取舍、交接 | 决定理由、已有授权依据、受影响对象及执行状态；超授权事项先提方案，不能先做后报 |
| 预计完成时间、里程碑或检查点变化 | 发现可能偏离即报原因、影响和修订预期，区分预测与已确认承诺；到期无结果也交等待原因与下一责任人，不能静默顺延 |
| 完成、取消或退出 | 成果、验收状态、未决效果、未读结果与写权交还分别说明；保留遗留承接 |

同一事项按原任务、结果版本和实质变化去重；无变化时保留原记录，到约定检查点再交必要状态，合并可合并的更新。默认只传结论、影响、证据引用、需决定事项与下一步，不搬运完整日志。无推送能力时，协调员按约定保存更新并交可定位引用，由已明确的获准拉取者在检查点读回；未实际读到不能标为已汇报闭环，通道故障仍有补交责任。

G8 接收协调员汇报后，负责向用户说明关键成果、承诺变化、重要风险和需用户决定的事项，合并跨项目信息并如实说明未验范围；无需逐条转播协调层的内部过程。协调员对 G8 的汇报、G8 对用户的沟通与项目负责人的业务验收分别留证，不以其中一项代替另两项。

## 3. G8 小迭代直派

用户已允许 G8 直接唤起 Codex Cloud 做独立小迭代。满足以下条件即可沿有效授权执行，无须再为使用这条路线逐件请示：

1. **成果独立**：目标、输入、输出和检查清楚，能形成一个有界交付；不要求协调多个项目的新决定或频繁重新分派。
2. **范围可控**：在已获准仓库／资产内，改动可审查、可撤回；调用、时间和写入范围有界。文档、局部修复、补充验证可以适用，具体仍看影响。
3. **依赖与权限成立**：所需资料、工具和环境实际可用；不隐含新增部署、生产写入、凭据变更、付费许可或超预算动作。现有阶段冻结和生产限制继续适用。
4. **没有冲突**：核原任务、已有分支／PR／Cloud 执行和未决创建；没有另一派发者在做同目标，也不争用原写者、共享接口或资源。不同分支名不自动证明没有语义冲突。
5. **有人收尾**：G8 承担这次派发、结果拉取与异常跟进；成果归原项目，按约定交负责人集成和验收。组织自身协调成果可由 G8 验收，不借此获得项目生产写权。

| 情形 | 协调层知情或承接方式 |
| --- | --- |
| 无项目实施影响的独立组织整理／比较 | G8 可直接完成并在原任务合并回报，无需另建协调单 |
| 属于项目、满足上述条件，形成独立候选改动 | 开始前在原正式任务留下目标、范围、派发者和执行关联；向既有协调／负责人通道提供可追溯摘要，结束后交版本与验证。知情不等于新增审批 |
| 通知暂不可达，但独立授权、输入和无冲突证据齐备 | 仅推进不依赖接收者新决定或共享写权的工作；记待送达、G8 跟进责任及检查点。不能把沉默当接受，也不能因此跳过负责人验收 |
| 涉及在途项目计划、共享资产／容量或需要新的项目决定 | 在相关写入或占用前由协调层和负责人安排；等待时可继续独立获准的只读分析 |
| 执行中超出独立性、预算或边界，或需要反复续派 | 停止受影响的新增动作，将原任务、已有产物和未决执行交协调层；其他无依赖工作继续 |

已有有效任务包或长期授权直接复用；缺失的通知、任命或执行回执分别记录，不能为填写完整而编造。派发记录与正式入口规则仍按[任务追溯](../skill/organization-collaboration/references/task-traceability.md#派发与恢复)执行。

## 4. 协调员指挥 Cloud 路由

以下为目标职责合同，**尚不表示现有协调程序能够触发 Codex Cloud**：

| 职责 | 决策与交付 |
| --- | --- |
| G8 | 提供完整目标、优先级、授权和跨项目约束，接收阶段结果；在确需用户决定时集中沟通 |
| 项目协调员 | 在既定目标和授权内统筹各项目负责人、跨项目资源、调度顺序及 Cloud／本地路线；结合负责人审定的业务任务包，在已有预算内安排执行与检查点，指挥 Cloud 路由并跟踪回传，不替代负责人业务验收 |
| Cloud 路由执行者 | 核完整任务包、目标环境和已有执行；承担一次原生创建／获准续发，保存真实引用，拉取状态与产物，沿原任务交回协调员。工具只能回到 G8 时，G8 可作已约定的中转者 |
| Cloud Worker | 在允许范围内实现、自检并交精确版本、证据、未验项和阻塞；不能自行扩大目标或继承其他端权限 |
| 项目负责人 | 决定业务范围与项目取舍，组织必要独立复核、集成和最终验收；向协调层回报 |

“Cloud 路由”是一项执行职责，可以由具备获准原生入口的现有参与者承担，不要求新建服务或常驻角色。每次任务包明确：协调员负责派发决策和跟进，谁是唯一实际调用者（`dispatch_owner`），谁拉取、谁接收、谁验收；另一入口不得并发再建同目标执行。协调员可在既有授权内安排续发，路由执行者须先核原任务状态，不能只因收到重复指令再次创建。

**当前可用边界：** [协调核心](../scripts/project_coordinator.py)与[传输层](../scripts/coordinator_transport.py)业务请求只接受 `QUERY_BLOCKER`。已有单件连通性探针是独立限定回执，不是通用执行入口。信箱提交只保存数据，不创建 Cloud；已发布环境也不证明协调员拥有 Cloud 工具或权限。不能把目标交办、代码修改或生产指令塞入查询正文，称作协调员已接单执行。

当前项目任务可沿已有获准通道把已审任务包交 G8 代建；符合第 3 节的工作也可由 G8 直派。若只有查询入口，先准备完整目标包并明确“待执行入口承接”，只发送真实阻塞查询。后续验证协调员路线时须取得其真实身份与授权、Cloud 原生创建引用、同任务的精确产物回传及负责人验收证据，并覆盖重复请求、创建结果未知和取消后的对账。一次 G8 直派成功不能替协调员路线验收；本轮规范不部署或新增该能力。

## 5. 幂等、异常与移交

用原正式任务引用、成果范围、输入版本和派发意图识别同一工作，关联平台实际返回的任务／回合。它们是对账依据，不宣称 Cloud 服务端提供幂等或恰好一次执行。

| 情况 | 必须采取的动作 |
| --- | --- |
| 同目标同输入已有执行，或重复收到指令 | 复用原引用查状态与产物；不另开任务。改变输入时登记新版本、影响及对旧执行的处理，再决定是否需要新执行 |
| 创建／续发超时、受理不明 | 保留 `UNKNOWN`，原派发者沿原调用对账；一次空列表、无回复或过期快照不能证明未执行，不改入口重派 |
| 原生创建成功，记录回填或结果通知失败 | 保存原生引用、产物和待补写项，补原记录／原结果；不重新运行已成功部分 |
| 权限或环境故障 | 明确失败动作、目标、原因、已发生效果与停止点；原任务内有界排障，交对应维护者。授权缺口由 G8 汇总给用户，不能复制凭据或换路绕过拒绝 |
| 需要协调层接手 | 交原任务、目标／边界、输入与产物版本、原生执行、当前写者、UNKNOWN、预算余量、待交付结果及下一检查点；收到明确接手回执前，原派发者继续跟进 |
| 取消、撤权或写者切换 | 立即约束相关新动作，沿原执行核停止、已发生效果与写权交还。通知送达、任务取消和进程已停分别留证；旧写者未交还，不放行冲突写入 |

实现问题在原范围和预算内处理；项目范围／依赖／优先级问题交协调层与负责人。既定目标、优先级、授权和预算内的跨项目调度由协调员处理；超出这些边界的取舍、新授权及超预算事项交 G8，其中确需用户决定的再集中提报。升级必须带可决策的证据与选项，不能只把整段日志向上搬运。协调员暂不可达时保持原任务与恢复责任，不自动任命新负责人或直派生产。

## 6. 验收、反例与回看

每次交付保留原任务、输入版本、提交／PR／产物引用、检查方法和覆盖范围、未验／UNKNOWN、下一责任人。依次区分原生受理、成果保存、作者自检、所需独立复核、负责人验收、结果实际读回与写权交还；草稿 PR 或退出 0 都不等于已采用。按风险选择检查，不给小改强加生产级验收，也不因改动小略过项目必验项。

| 场景 | 路由判断与可检查结果 |
| --- | --- |
| 用户要求整理本仓规范，输入完整且无冲突 | G8 可直派 Cloud 形成草稿 PR；记录验证与未实现能力，合并、部署和项目采用分别由相应决定支持 |
| 局部修复原本独立，后来需改共享协议或多项目接口 | 在扩范围前移交协调层；保留已做补丁和原执行，不能拆成多个小改继续越界 |
| 一行修改即可重发凡人音频 | 改动虽小仍影响生产许可及现任负责人。走项目流程，查询入口不得生成音频 |
| 凡人负责人暂未回复 | [已绑定负责人](project-coordinator.md#可信入口核验p0)的存在不能由一次失联推翻；沿原请求查询／恢复，禁止重复补位与生产派发 |
| 协调员要求 Cloud 修复，但目前只有 `QUERY_BLOCKER` | 目标包记待承接，或沿获准代建路线继续；信箱 ACK 不能证明 Cloud 已创建 |
| Cloud 无回复而协调员提议再建一次 | 保留原任务 UNKNOWN 并对账；只有确认未执行且当前授权仍有效，才按原意图处理未发生动作 |

在原任务按实际证据回看：有效成果、人工转述次数、等待原因、重复派发／冲突、未决项年龄及验收成本。直派若持续产生协调返工，后续同类任务改由协调层承接；协调层若把已授权小改变成逐步审批，缩减重复交接。调整的是受影响范围的规则，不为改善统计把未验改成通过，也不重启在途任务。
