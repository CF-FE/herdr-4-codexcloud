VPS 文件日志与 journal 有重叠，以上以 journal 为准；两端计数也不能相加换算为掉线次数。Win 采集排除了两行含敏感字段的日志。VPS 文件尾落后于 journal，Win 警告日志末条为 11-05 14:50:32.750，末端缺少连续成功心跳；安静、缓冲或采集滞后的区别未确定。这些是实际保留事件数，不是全天丢包率、业务失败率或完整断网次数。

唯一 60 秒观察得到：

- ICMP **30 发、22 收、丢 8，约 26.7%**；成功 RTT 最小/平均/最大为 **251.489 / 264.795 / 316.647 ms**。
- 4 个 EasyTier 快照均为 UDP 直连，peer 未变，软件 loss 指标均为 12%。软件 loss、ICMP 丢包和 RPC timeout 是不同量，不能互换。
- 3 次 VPS → Win 只读 SSH 命令均成功，总耗时为 **4.919、4.524、6.932 秒**；这不是纯握手时延，也未验证长连接跨故障恢复。
- Win 在 15:03:29.040 进入连接待机。原输出没有每包绝对时间，不能精确拆分切换前后丢包率；整窗结果既不能排除省电影响，也不能外推全天质量。

## UNKNOWN 与兜底边界

UDP 丢包的具体位置和根因、连接待机的因果贡献、历史未记录路径变化、真实不可用总时长及业务影响仍为 **UNKNOWN**。没有同一 Hindsight 请求的 SSH、MCP 和 API 分阶段记录，不能量化其处理或传输耗时。现有 SSH 日志为成功认证后正常客户端关闭，没有独立证据认定 SSH 协议自身故障；SSH 成功也不消除已观测的网络丢包。STUN DNS 警告存在，但固定 peer 已直连、打洞关闭，没有证据证明修 DNS 会消除此丢包。

现有证据支持以下建议，不新增执行授权：

1. 沿已批准合同容忍暂时不可达和连接重建，采用既定长超时、单层有限重试和总预算；保留明确的不可用/超时状态，不据此扩大重试、缓存或队列。
2. MCP → API 属于协议或会话层兜底。同一 EasyTier/SSH 路径不可达时，API 同样受影响，不能记作网络冗余。仅 MCP 初始化、发现或会话失败而底层可用时，API 兜底才有独立价值。
3. 写入结果未知先按原操作标识和结果回读对账；连接中断不证明上游未处理，不直接重放写入。在已授权代理实现内记录 SSH 建连/执行、MCP 初始化、Win API 处理的起止与结果。
4. 由实施者管理服务时段和保持唤醒；电源策略调整另依其有效授权。此举只控制已知主机状态变量，不承诺修复底层丢包。当前没有足够证据支持直接升级 EasyTier、改 MTU、ACL、路由或切协议。

原报告曾提出一次保持唤醒的 10 分钟验证方案，**未执行**。公子随后明确要求“不用对 EasyTier 反复测试，有个大概就行，给兜底方案做依据”，调查因此以现有材料收尾，不保留追加探测任务。原调查状态为 `READ_ONLY_INVESTIGATION_COMPLETE_WITH_UNKNOWNS`，闭环状态为 `INVESTIGATION_CLOSED`；这是调查完成及设计依据，不代替后续实施和工程验收。
