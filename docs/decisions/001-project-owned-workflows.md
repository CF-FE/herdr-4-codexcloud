# ADR-001　项目拥有工作流代码和记忆

2026-11-05 · 已采纳。公子在本次设计讨论中确定「程序负责执行，模型负责决策」，要求负责人生成项目工作流、在项目主仓独立迭代，并授权按开发文档实施。本文记录架构选择，工程交付以开发文档的验收项为准。

## 要解决的问题

同一个项目换 Worker 或中途断线后，接手者要能找到规则、已作的判断和原任务回执。把每个步骤留给模型临场重述会导致漏项和重复派发。凡人批次交接还暴露了另一个区别：清单可由程序核对，是否开工由现任负责人决定。[项目主仓规范](../coordination-policy.md#项目主仓与项目级规范)

## 决定

- 协调仓提供生成源码的轻量工具。由现任负责人在已有 Herdr 身份下设计第一版，程序把约定的阶段和分支生成到项目主仓。项目可以直接修改源码并自行发布。首版选 Python 3.10+ 标准库，沿用协调仓和目标机已有的运行方式。
- 已知规则直接执行。只在需要判断的分支向相应角色提出带证据的问题。一次有效决定可以覆盖整个批次；程序保存选择后推进。技术步骤结束时产出清单和回执，业务放行归原单指定的验收者。
- 每项目一个记忆入口，保留长期决策、资产索引和交接规则。短期进展沿原 Issue／Project，运行检查点留在执行侧。各工作流链接同一份项目记忆。
- 本地流程调用项目自己的确定性函数。需要其他角色或机器时，准备好交办内容，由已有 Herdr／Cloud 路线承接，再导入原生结果。仓库版本、模型输出和机器间连通性各自不能证明某次派发成功。

## 取舍与复议

Deer 的 `create` 将设计固化成源码，`run` 重用源码，值得借鉴。直接采用其 Runner 可以得到现成的并发和事件，但其运行 ID 按调用生成，示例会过滤失败项，项目仍要自行处理原任务恢复和缺项。组织统一托管每个流程也方便集中升级，却会使项目运行依赖协调仓发布。首版选择源码生成，代价是公共修正要由各项目自行选取。等两个项目确实重复维护同一执行能力，再根据实际维护成本提取版本化库。[Deer 创建入口](https://github.com/deerwork-ai/deer-workflow/blob/b208230/src/cli/create.ts) · [Deer 工作流实现](https://github.com/deerwork-ai/deer-workflow/blob/b208230/src/flow/workflow.ts)

具体接口、工程分工和验收见[开发文档](../project-workflow-development.md)。
