# ADR-003　审批作为可接续的协调子工作流

2026-11-06 · 已采纳，待实现与部署。公子在原主会话提出将审批链做成工作流，随后明确“推进执行”并要求沉淀设计。采纳范围是[审批子工作流设计](../approval-workflow.md)中的状态、责任、真实投递／答复回流及原任务接续，不代表入口已经可用或任意业务动作获准。

## 问题与依据

凡人 Win 制作入口恢复申请曾只留在协调员自身会话；随后提问工具的受理被当作用户端可见，内部跟进反复等待答复。现有提醒程序只唤醒协调员，收件器只消费其自身标记，未形成可靠的审批上行和答复回流。继续增加提醒频率不能补齐这条链路。[现有待办机制](../project-coordinator.md#native-followups) · [原项目](https://github.com/CF-FE/fanren-work/issues/2)

## 决定

- 在协调层补充按需审批子工作流，复用现有私有状态、事件、跟进和记录通道；项目保持自己的流程与运行检查点，不新增独立审批平台。
- 先核已有授权。只有新增授权或明确要求决定的动作进入审批；普通执行、已授权的低成本重跑和可选人工听审不扩大为全流程审批。
- 分开记录投递、决定、执行与核收。工具受理不能代替到达指定决策入口；有效答复可直接证明本次收件，不增加用户“已读”动作。
- 绑定稳定原请求、范围版本、有权者、真实决策入口和答复接回责任。程序计时、去重和接续，模型处理新判断；消息正文不能自行授权。
- 同一阻塞有明确最迟升级时间。无实质变化不能只改下一检查点；升级须有真实通道与责任人，通知行不是送达证明。
- 批准后沿原执行者、原意图和检查点接续。拒绝或撤回只影响相关动作，未知副作用先对账；批准、恢复成功及业务验收分别取证。
- 云端Dot感知并向公子汇报，业务验收仍由项目负责人或本单指定验收者负责。审批子流程不新增岗位，不改变 Herdr／Codex Cloud 的宿主分工。

## 取舍与复议

只靠自然语言提醒改动最小，但仍可能把等待转成无人接回的循环。独立审批系统会增加身份、状态与运维成本。本轮选择在已有协调合同内补齐状态和适配器，代价是必须为实际使用的用户入口维护可核的投递与答复方式。

普通业务继续异步回填、不等待云端Dot在线或已读；只有确实需要新决定的分支等待。审批本身的拒绝、失败或取消应明确结案，不伪装成业务完成。

本记录补充 [ADR-001](001-project-owned-workflows.md)的决定与交接机制，不取代其项目自有工作流、程序执行／模型决策和验收分工；[ADR-002](002-shared-project-memory.md)的记忆边界不变。设计细节、实施切片和验收只在[唯一设计文档](../approval-workflow.md)维护。
